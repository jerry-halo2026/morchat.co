# 统一工作台、工作首页与角色面板

> 2026-11-06，方案收敛阶段。当前设计方向：Multica 为统一产品与唯一任务/调度基座；Paperclip 借鉴公司治理；OpenMausBot 借鉴人机协作操作链；Evose 借鉴整体产品组织、项目工作面及知识能力上下文。设计方向不等于企业 P0 验收或正式开发授权。沿用既有文档与证据，不另建第二套设计文档。

本文已将工作入口、组件来源、任务控制和版本展示正文迁移到 Multica 唯一底座。Paperclip 仅企业治理参考及独立源码候选，OpenMausBot 仅协作机制/独立 helper 候选，不带入整套 chat/store/runtime。C01–C08 仍为 DRAFT，以下“必须”是验收要求，不是现成功能声明。

**2026-11-06 优先级确认：**外部文档 CLI/MCP 核查到此收束，先跑统一客户端交互与 Agent 协作（PLAN §0.2）。主线为“我的工作→目标/项目→小队与认领→任务线程 @Bot→本地执行/追问/审批/停止→自动归档→成果验收/用量”。知识/业务表连接器后接；不能因此推迟任务、附件、上下文和设备的授权/撤权。当前使用的旧低保真与参考项目页面只能作参考，不是 Multica 新主线已实现的证明。

## 1. 直接回答用哪套

| 使用者/场景 | 当前设计 | 不采用什么 |
|---|---|---|
| 员工日常工作 | Multica统一客户端为基础，“我的工作”首页，进入项目/任务线程、对话、Bot与资产 | 不让员工切换Multica/Paperclip/OpenMausBot三套应用 |
| 部门负责人 | 同一客户端的本部门目标、待处理、交付与授权跨部门项目视图 | 不把Squad、Agent汇报树或工作区成员关系直接当部门权限 |
| 老板 | 同一客户端的公司目标与治理面板，按授权查看经营与协作 | 不把全公司管理员权限作为日常身份，不用消息量代替成果 |
| 运行与异常处理 | 同一Multica运行记录、客户端daemon诊断和受控企业治理入口 | 不嵌入另一个带管理员凭据的Paperclip后台 |

整体复用Multica现有导航、任务/项目、Agent/小队、线程、附件和统计组件；“我的工作”和部门视图按真实角色适配，不重新画一套同类基础UI。Paperclip用于治理规则、组织/目标/审批/预算/审计对照；Evose用于整体产品组织、项目工作面、知识与能力上下文，以及日常使用/能力维护/企业治理的分层体验；OpenMausBot用于下述协作操作链。引用项目不等于增加运行依赖，功能最终使用同一套身份、任务、文件和版本关系。

2026-11-06 登录态深读补充：Ethan 明确看板、流程、排期及项目知识和能力均属于整体工作面，不应只把 Evose 当资料库参考。看板显示任务状态，业务流程显示阶段推进，甘特/排期显示时间与依赖，它们应关联同一项目任务；不因为术语不同排除，也不把业务流程误当自动化工作流引擎。项目规则、能力、知识库、记忆为人和 Bot 提供协作依据，需连接现行版本与权限契约。当前实际看见 Evose 看板/业务流程和规则页面，未见甘特时间轴；其另一个“计划”入口是定时执行。详见 [Evose 产品研究](EVOSE-PRODUCT-RESEARCH.md)。此轮确认参考方向，不改变既定首轮多人协作范围，也不将完整流程配置、可编辑排期或外部知识引擎自动加入首轮。

## 2. 员工体验与 OpenMausBot 的关系

**OpenMausBot仍有明确价值，不因Multica成为基座就删除前期研究。**已有源码深读用于确定具体交互与反例，而不是再移植一个聊天窗口。

- **组队与岗位包**：员工/负责人都能选择真人和Bot、说明职责、资料与工具范围；预览模板差异。基于Multica Agent/Squad补缺口，侧栏分组不当权限墙。
- **讨论与派工**：各Bot回复可区分，工具过程可折叠；结构化@选中目标后直接发送。显示、上下文与唤醒分离，普通群消息不启动全群Bot。
- **追问与审批**：问题卡显示等待谁、属于哪个任务/运行；回答和许可可追溯、可恢复、发送时重验权限。不能因为OMB有卡片就宣称DSH审批接入已完成。
- **补充与停止**：用户知道补充进入当前轮还是下一轮，停止单Bot还是整次协作。未验证实时steer时不承诺即时生效；停止回执与停止请求分开。
- **文件交付**：任务中看到来源、生成/待上传/已归档/已验收状态，能预览和回源。本机路径不是公司已收到的成果。
- **记忆和skill维护**：看到来源、修改差异、候选版本、评审和发布；发布后新任务使用哪一版明确，旧运行不静默漂移。个人Undo或模型review不是企业版本安全保证。

源码策略：Multica有合适实现就直接复用；缺失时再评估OMB独立展示/校验子件；必须替换其数据访问、授权和事件入口，不能带入另一套Store、任务引擎、skill库或公司账号后台。详细固定源码证据与禁用行为见 [复用§1.1及历史深读](REFERENCE-REUSE.md)。

首版统一桌面客户端包含本地执行管理；浏览器为辅助协作入口，不自动取得本机工具权限。原生移动端先保留架构空间，未经本轮Windows实测不能宣称已交付。OMB远端Client停本地harness的模式不采用；沿用Multica客户端/daemon主路径。

原生 Multica 单 Agent 对话不能替代企业多人群；原生 Squad leader 限 Agent，真人业务负责人是企业语义映射/扩展，不能直接把真人 ID 写入 Agent-only leader 字段。两个缺口在同一 Multica 后台补齐，不通过引入 OMB 后台绕过。

### 2.1 群里的 AI 在哪里工作

员工工作助手默认在其本人指定授权设备运行；部门公用 Agent 自动选择预授权设备池内符合数据、能力、资源与容量条件的节点。不是谁 @ 就用谁电脑，也不是都用群主电脑。入群不授予设备使用权，公用 Agent 的维护人不必亲自在线才能由其他合格池节点执行。

AI 名片展示归属/维护人、可服务范围与执行策略；有权者可配置设备池，普通群成员不因此看到全公司设备清单。任务卡展示 Agent 身份、实际执行位置/变更原因、状态和交付版本。池内自动选择无需逐次人工批准，但每次验权；员工助手超出默认设备的转移要明确授权。

群共享获授权的消息/目标/任务/资产，不共享私人文件、其他群、浏览器登录和完整个人模型会话。多 AI 通过明确子任务/交接协作，普通回复不产生新的 Agent 唤醒。详见 [群协作与设备池](DISTRIBUTED-COLLABORATION.md)。

## 3. 工作入口的最小组成

以下是能力清单，不是把每项都做成一个一级菜单；统一导航建议见 §3.1。

| 入口 | 员工看到什么 | 与业务事实的关系 |
|---|---|---|
| 我的工作 | 待认领、我负责、等待我补充、我关注的交付 | 查询任务权威状态及自有交接请求，不另建状态 |
| 部门业务 | 本部门普通任务明细及目标关联、工作阶段、交接和阻塞情况 | 员工与负责人均可用；普通任务默认同部门可见，敏感内容另授权 |
| 跨部门协作 | 获授权项目或任务的明细、进度、交接、阻塞和交付 | 同一工作台按授权范围呈现业务流转，不展示对方整个部门 |
| 工作群 | 人与 AI 消息、@、附件/链接、任务卡、阶段成果 | 每条消息有真实发言身份和来源；引用任务需独立授权 |
| AI 同事（Bot） | 可用 Bot、职责、维护人、模板来源、能力版本和当前就绪情况 | 实例映射同一个 Agent；升级/换设备/新任务不创建影子 Bot |
| 目标与项目 | 自己参与或有权查看的目标、任务与成果 | 展示目标/任务关联和责任，群不强制一对一绑定项目 |
| 设备与运行 | 本人默认设备、有权管理的公用 Agent 池、版本/能力、并行运行、局部等待原因、待归档大小，单任务取消/设备暂停/撤销入口 | 入群不入池，按权查看；自动选机与已执行分别展示，不公开无权设备清单 |
| 用量与设置 | 自己可见的用量；负责人/老板增加获授权预算汇总和管理操作 | 使用模型、查看成本、管理预算、管理 Key 分开；员工不填写供应商 Key |
| 资产 | 可访问的成果、知识、skill；我维护/待评估的条目 | 资产所属公司、维护人与可见范围分开展示 |

员工与负责人都有部门面板：本部门普通任务明细及其流转默认同部门可见；负责人另有所负责部门的管理操作。跨部门参与者也能在同一工作台查看获授权项目或任务对应的业务流转。老板增加公司目标、部门交付和有来源的业务指标。不是老板独享面板，也不是三个独立应用；查看权限不自动授予修改、分派或管理权限。

### 3.1 前端定位：以工作为中心，不拼接参考产品

**已确认：**员工、负责人、老板使用同一工作台；默认首页为“我的工作”，先展示今天/当前待认领、待处理、待交付、待确认的事项，再从侧边栏进入对话列表。无截止日期和逾期事项不能因“今天”筛选消失；P1 期限/逾期展示先冻结 C02 的截止日期来源和时区，不从创建/运行时间推算，缺契约时显示当前待办/未设期限，不伪报逾期；通知、任务和待审批不是三份重复待办。负责人和老板增加获授权视图/操作，不换一套产品。

方案取舍：聊天优先容易把未完工作埋在消息里；采用“我的工作＋协作对话＋同源任务/资产视图”。统一使用 Multica 客户端/后台，不并排运行参考产品，不再采用 Paperclip 前端或原生对话作为当前实现底座；不是完整 OA/IM，也不是把管理权限换皮给员工。

以下侧边栏分组为推荐信息架构，名称、顺序和视觉密度待低保真评审；不影响已确认首页：

| 推荐分组 | 内部内容 | 唯一实现 / 首版露出方式 |
|---|---|---|
| 我的工作（默认首页） | 待认领、待处理、待交付、待确认；阻塞/待同步；最近工作 | 从 Multica 任务/run 与待处理命令投影，企业待办聚合须适配；不复制状态机 |
| 对话 | 获授权工作群、Bot 对话、任务线程 | 沿 Multica 线程与任务关系适配企业受众；普通发言不派工 |
| 工作 | 目标/项目/任务列表、看板；部门/公司/获权跨部范围 | Multica 同一任务详情；原生项目甘特保留；企业排期差异按 P2 评审，非 P1 硬门禁；写动作仍受授权/日期契约约束；不加工作流画布 |
| 组织与 AI | 真人部门/成员、Bot 名册、小队、岗位/模板与就绪缺口 | 复用 Multica 用户、Agent/Squad；真人部门与资源授权明确补缺，组队关系不是权限墙 |
| 资产与能力 | 成果、知识、skill、岗位/Bot/小队模板和版本来源 | 复用 Multica 载体并补授权/保留版本；知识表格连接器后接，不导入另一套 Studio/正文库 |
| 应用与连接 | 获准来源、动作范围、过期状态与模型可用性 | 核心链先用最小受控工具；外部知识/表格后接。普通员工仅见有权连接，Key/路由管理另限权 |
| 用量与治理 | 我的用量；获权部门/公司费用、预算及审计 | Multica run 与真实用量证据关联；预算/企业归集待 B08/C08 验证，不继承参考产品账本 |
| 底部：设备与运行、设置 | 本机/授权池、等待原因、待上传、诊断及个人偏好 | 本地 DSH/daemon 关联 Multica run；配置与适配器管理不混入普通员工设置 |

这是完整功能分组建议，不要求首屏平铺七个大菜单：高频我的工作/对话/工作固定可见，组织/资产按职责展开，连接/治理可收在“更多/管理”，设备/设置在底部。无权分组不露出，有权但未配置显示真实就绪原因；具体标签/顺序仍待低保真评审，未把新建议记为已确认范围。

部门/公司范围由真实授权决定，不靠切换菜单扩权。跨部门授权只出现相应项目/任务；可以收藏入口，但不另造跨部门任务库。组织架构、权限、费用管理入口按权置于相应视图/设置，不为老板单独做门户。首版不做任意自定义导航、插件页面市场或多产品 iframe 拼盘。

### 3.2 对话、任务线程与执行详情

- **群主时间线：**每个实际对群发言的 Bot 独立署名，展示结果、问题和重要交接并关联任务。完整回复在该消息/任务线程可展开；负责人总结不覆盖原文。多个 Bot 同时交付时按任务组织，不只留最后一位。
- **任务线程：**从群卡、首页待办或工作面板进入同一个 task ID 的讨论视图；查看参与者回复、交接、文件版本和待决问题。不同入口打开同一任务详情和有权讨论，但各消息/附件仍单独验权。同任务可有不同受众的线程，不拼成一个跨群广播窗口；从首页/面板发言先选择线程/讨论域并显示受众，回复沿用当前线程，未选不发。私密群内容不会因链接了普通任务就出现在全部门线程；来源不明的正文不扩播。
- **执行详情：**同轮过程说明和连续工具活动折叠，进度更新原卡，不把每个日志事件发成新群消息。审批、阻塞、失败与停止原因必须可发现；系统收件回执标为系统，不冒充 Bot 已经思考。
- **一个输入框，@ 后发送：**已确认取消“普通讨论 / 请 Bot 处理”模式选择。群与任务线程内输入 @，从有权候选中选中具体 Bot，直接发送即提交该目标的提问/委派；没有执行型 Bot 提及就是普通消息。选中项保留稳定 Bot ID，不由后台扫正文猜目标；同名展示归属以消歧。仅写名字、未解析文本、引用/代码/粘贴及 Bot 输出中的 @ 不产生新的执行授权。发送前可见本次目标；未识别/失权目标明确报错，不静默换人或群发。编辑已发送消息只改消息修订，不改变已准入任务；修改工作指令要新发一条 @ 请求并关联原工作；已存在追问/审批/待处理补充的专用按钮走关联命令，不需再 @，见 §3.5。授权范围/费用与任务关联可查。
- **结果不作假：**本地出现、待同步、团队已收到、任务已验收分开；Multica 任务状态、运行状态、自动保存与业务验收仍按 §5.3 展示。没有 provider 原始增量就显示正在处理/已完成消息，不伪造逐字生成。

公开工作回复不含模型隐藏推理或原始秘密。用户可看的消息、某 Bot 可消费的上下文、会启动哪个 Bot 必须分开处理；精确触发/防重规则唯一见 [群协作 §4](DISTRIBUTED-COLLABORATION.md)。

### 3.3 统一界面契约与首版体验门禁

整个产品以 Multica 客户端/后台为基础，共享应用壳、路由、身份/资源范围、设计变量和组件；任务卡、稳定 Bot ID、消息、资产与版本各有唯一语义。数据读写沿 Multica 权威入口补企业准入，不直连数据库绕过权限。Paperclip 只贡献治理参考或经依赖/许可审查的独立源码；OMB 只贡献协作机制或独立 helper，不能引入其 Store、私有 API、自动路由、账号或 runtime。具体组件抽取与桌面分发按当前证据评审，不凭名字假定能力。

共享的空态、加载、失联/同步中、过期数据、无权、失败与重试状态必须先约定；禁止假成功、无权先渲染后隐藏、通知/计数泄露内容、复制原生按钮却缺后台权限。AI Markdown/链接/附件按不可信内容展示，不可借渲染调用本机 IPC/工具。待办、运行、保存和验收各有一致标签，不把不同含义都叫“完成”。

B02 指定一个前端集成 owner 管应用壳、设计变量、共享卡片和展示 DTO；页面 agent 只在冻结边界内开发，不各装一套 UI 库/状态框架/路由器。具体协作与合并门禁见 [工程基线 §5](ENGINEERING-BASELINE.md)。

P1 先用“首页待办→任务线程→稳定 @ 派工→两个 Bot 各自回复→进度/文件→返回首页”验证，不先铺满页面；P2 扩部门/公司与资产版本，P3 角色和异常回归。跨入口身份/状态一致，受限来源不因跳转泄露，断线不伪称送达，键盘/可读标签及待决事项不依赖颜色。首页及 Multica 唯一底座已定；布局、组件边界和接口仍待相应实施门禁，不阻塞 P0 证伪。

### 3.4 低保真：同一份工作，五个入口

### 3.5 完整操作链：一个工作台内做人机交接

操作按对象定义，不按参考产品划页面。Multica task/run 是唯一工作事实；追问、审批、补充、停止由同一后台的持久命令记录与 DSH 回调关联，具体存储/接口待 C02 验证。参考产品 interaction/queued-comment 卡片只能提供机制证据，不能假称 Multica 已有对应 API；同一事项在首页与线程处理一次即同步，不建第二审批/队列权威。

|---|---|---|
| 回答 Bot 追问 | 问题、原任务/Bot、选项或补充输入；区分“答案已记录”“待送达本地执行器”“已消费/需重新确认” | 有当前回答权限的人才可提交；负责人不是自动代答人。指定真人回答的问题不由另一个 Bot/默认值代答；历史回答不改写，变更形成新要求 |
| 批准或拒绝一个动作 | 具体请求、资料/工具范围、用途、有效期与本次影响；明确拒绝/过期/撤销 | 不是“全权允许”；批准记录不等于执行成功。查看任务、批准工具、验收成果是不同权利；MVP 禁止的第三方写入不能借弹窗放行 |

| 停止本次协作 | 预览本 root 的运行、子任务及待处理要求；关闭该范围新增工作并逐项停止，展示未停/无权项 | 不停止其他 root/同一 Bot 的无关任务；不会因重连、旧补充或子项迟到自动重启。新授权“继续”才允许后续运行 |
| 停止并按新要求继续 | 独立、明确命名的中断操作，展示将使用的新要求和实际执行状态 | 这不是普通“停止”；旧执行未可信终止/效果未核对不能直接重放。未验证能力不显示可用按钮 |
| 查看 / 提交文件 | 本机产物/待归档 → 公司已确认版本 → 已提交待验收 → 已验收；消息附件和任务成果打开同版 | 同部门可读不等于可验收；指定有权验收人针对确定版本验收。退回改为新版本；旧链接不漂移；撤权后预览/下载拒绝 |
| 配置 Bot / 小队 | 配方草稿、将新建/绑定/变化、版本差异、所需权限、缺项和部分失败；员工与负责人均能在授权内维护 | 小队优先绑定既有真人/Bot；职责、工具、资料和设备分别就绪。模板导入不复制旧记忆/授权；发布和现存实例升级另行明确，不自动热改 |
| 纠正记忆 / 改进 skill | 展示本次实际加载知识的来源/范围/版本；纠正知识或提出方法候选，保留差异和评审记录 | 不展示整个私人 HOME。知识后接选定内容服务版本，skill 用核验后的版本/评估链；Undo/回退也是有条件的新变更，不复活权限；自动记下不等于公司发布 |

案例“跨部门活动方案”：周然为运营负责人/父任务业务责任人；林悦为内容部协作者，只获该项目授权，不获得运营部全部业务。两个 Bot 使用登记的授权设备池。演示角色拥有的补充/验收权来自明确任务授权，不是头衔自动赋予。

1. **员工进入：**林悦在我的工作认领 ACT-101 资料整理，进入项目群，看到周然、资料 Bot、内容 Bot 和两个任务线程。普通留言只产生消息。
2. **双人派工：**林悦 @ 资料 Bot 处理 ACT-101；周然 @ 内容 Bot 处理 ACT-102，或有权者同一条消息选择两个目标。保留父任务真人责任；不同目标独立 run。演示同时显示两台合格设备上的并行工作。
3. **协作补充：**内容 Bot 请求验收口径，作为一个持久问题同时投影到周然的我的工作、收件箱与原线程；林悦可看获权状态但不能冒充指定回答人。周然回答后显示记录/消费状态，而非自动批准所有工具。
4. **Bot 交接：**资料 Bot 产生的 v1 先自动归档，内容 Bot 再消费获权固定版本。其他独立工作可先并行；等待资料不占用不可释放的执行槽。各 Bot 原回复保留，不由 Lead 摘要覆盖。
5. **归档与用量：**内容结果先显示本地已生成/待归档；断网时同事不能打开公司不存在的文件。中央确认后显示版本与来源 run；用量标示真实/未报告/未知，演示数字永久标“样例”。
6. **负责人验收：**周然在收件箱打开同一版本进行验收；林悦能查看结果但无该验收权限。任务完成、收件箱与成果状态同步，不能以模型结束或已读代替验收。失败分支保留停止/归档待核对而非强行成功。
7. **后续复用：**从成果查看来源、规则与实际使用版本；下一期形成改进候选和小队/skill 模板。不会因验收一次就自动发布公司技能。

角色切换和进度推进是演示控制，不表示真机实测。完整首轮真实验收仍按 MINIMUM-CHAIN §1.2/MC-08，包括同 Bot 多线程、权限拒绝、多目标局部失败、根停止与防风暴。

#### 界面必须解释的负例

- 私群无权、来源撤权：不展示正文/缩略图/摘要；仅在资源存在性允许披露时显示受限提示。项目参与不能绕过私群权限。
- 无合格在线设备：显示等待哪类资格/设备，不变成无人解释的“排队”，不借其他人的电脑或中央执行。
- 一个 Bot 失败/停下：另一个任务继续；停止单 run 与整次协作范围分开，离线只显示停止待确认。
- 未归档、用量未报告、费用未知和未验收均独立可见；视图间共享对象和修订，刷新不把未知改成成功。
- 未来预览明确标 P2/P4；首轮不显示可点击但无真实支持的发布、排期编辑或工作流执行按钮。

#### 本轮设计验证记录

已用本地预览走查员工认领/普通留言、两真人分别 @ 两 Bot、看板/流程/排期/知识页、负责人回答、未归档禁预览/验收、员工无验收权、负责人验收后首页回流，以及离线/单 run 停止。修正了原型中“验收一份成果误标两任务”和“离线倒退已确认停止/归档”两处展示错误并复验。回答只记待消费，不假装执行器已处理。桌面与 360/320 宽度的窄屏排期已检查，所测页面无横向溢出；浏览器未记录脚本错误。语法/链接检查与独立设计/定向状态审查完成。

以上仅是低保真合成状态的检查，不是多账号服务端鉴权、真实 DSH、自动归档/真实计量、防风暴或双机 P0 通过。完整审批、根停止、退回后新版本、跨设备恢复等只在文档规定，未伪称本交互稿全部实现；仍按现行任务卡和门禁验证。

### 3.8 运行治理的最薄呈现（首轮不增页面体系）

沿原生项目、Squad、Issue 评论、执行详情和 Inbox 补现有状态，参考 Evose 的分层，但不复制完整管理台：

- 对话建队展示真实小队/成员、业务维护与委托范围；设备管理人只作运行位置/责任说明，不能冒充发起员工或授权者。失败部分与成功部分分开，不只显示模型总结。
- 派工按目标展示已受理/拒绝/待设备/未知；成员原回复保留署名，汇总关联本次结果；“还缺哪项结果/待授权/待归档/待验收”基于服务端事实，不能用 completed 统一变绿。
- Inbox 区分需我决策、提及我、一般通知；问答和工具批准明确分开。批准展示实际动作与范围，参数/版本变更、过期或撤权后的旧按钮不可继续执行。复用现有待办，不首建通用审批引擎。
- 明确授权内 Leader 选人派工不每步弹窗；超范围说明谁可处理，但不泄露无权对象详情。无合格设备明确等待；单运行停止与整轮协作停止分开显示实际回执。
- 菜单/标题/入口优先消费原生路由配置；前端隐藏不能代替 API 权限。知识、表格、商业套餐、复杂治理编辑器均不加入这轮。

## 4. 员工如何完成一次工作

完整业务契约见 [六步产品流程](PRODUCT-LIFECYCLE.md)。入口仍在现有群、我的工作、AI 同事和资产目录内，不增加四套独立产品。

1. **提出目标：**员工/负责人均可直接创建或请组织助手澄清，展示预期结果、输入、责任人、期限和验收口径。普通讨论不逐句建单；明确 AI 提问/规划才创建可见轻量真实任务，追问沿用关联，任务外自动标题等模型功能首版关闭。
2. **组建人和 AI 团队：**推荐已有成员/AI，选择已有 Bot 或 Bot 模板/岗位包，再用小队模板映射成员，预览新增/复用、权限和资源缺项；Bot 模板创建 AI 同事，小队模板创建本次团队实例，不复制旧会话/记忆/授权。员工和负责人按各自权限维护，新增 AI 不等于可以立即运行。
3. **拆分认领：**任务卡展示来源目标、唯一主承接者、业务责任、输入版本、产出/验收、依赖和期限；自己认领或按权限委派。跨部门可读与邀请不产生任意指派权；双人竞争只能一方成功。
4. **协作交付：**员工助手默认本人设备，公用 Agent 自动选择授权池；完整 harness 在本机调用公司云模型，独立任务可同机/跨机并行，消息/取消/状态不受长执行阻塞。交接有接收回执和资产版本；自动保存、公司归档、提交验收、验收完成分开显示，尚未上传不能称已交付。
5. **复盘沉淀：**在原任务指出问题或成功依据，形成知识/岗位包/模板/skill 候选。评估、维护和发布权限分开；不默认读取私密群或把一次成功升级为公司规则。
6. **下次复用：**选择已发布组合版本，映射新的真实成员和输入，重新验权；实际加载版本可追溯，缺工具/不兼容/加载不符可见阻塞。模板更新不静默改在途任务，继任者不依赖原维护人电脑。

AI 组织助手可辅助受理、组队、检查缺项和复盘，但不是必经入口或超级管理员。关闭它后，员工照常手动建群、认领、交接、验收。岗位包区分已登记/已物化/实际加载/检查通过；小队区分草案/准备中/可用/部分失败。重试恢复同一操作，不重复建群建单。

小队可由真人负责业务协调，AI 辅助；不强制 AI leader 或“一群一项目”。以上产品标签不建立第二份任务状态，面板继续读取唯一事实。

### 4.1 用户看到的版本记录

Bot 详情区分来源模板、当前生效能力、修改记录和任务运行；能力页关联配置内容版本、指令快照与 skill 版本，小队页区分模板版本与真实成员。是否已有可消费历史按 Multica 证据判断，缺口在 B03/B04 补齐；版本号不代替字节与加载证据，升级不换 Bot ID 或自动改所有小队。

变更记录展示操作者/时间、原因、前后差异、候选/评估/生效状态及影响范围。只有内容已系统保存、历史引用/GC 后可取且条件回退已验证才显示“可回退”；不能把 hash、活动记录或参考项目 history 接口当证明。回退列明配置/指令/skill，不回权限、不改旧 run。

这些在现有 Bot/资产详情内组合展示，不新增模板/版本独立产品；完整关系见 [产品流程](PRODUCT-LIFECYCLE.md)。

### 4.2 员工与负责人沿同一条活动方案走查

1. **员工发起：**从“我的工作”认领活动方案，选现有小队模板，预览运营同事、资料 Bot、内容 Bot 的绑定与资料范围；缺授权就待补，不克隆同事 Bot 或借其电脑。负责人也能从部门目标以相同流程发起。
2. **澄清与并行：**员工在任务线程 @ 资料 Bot 和内容 Bot。两项获准子任务并行；资料 Bot 问受众范围，首页与线程出现同一追问。员工回答后先见“已记录”，执行器收到显示“已送达”，对应 harness 实际消费后才显示“已处理”；内容 Bot 可继续不依赖该答案的工作，不等待整个设备队列。
3. **补充与许可：**员工追加“同时给出线下版本”，未消费前可以修改/撤回。确有授权需求时显示具体请求；有该权限的负责人批准一次范围内操作，不自动给所有下属或全部工具授权。下一轮补充不伪装成即时 steer。
4. **改变方向：**员工点“停止本次协作”，看到两个 Bot 和待处理补充的范围及各自回执；关机节点只能标待核对，另一独立项目继续。确认已停及效果边界后，员工明确继续/改需求，新 run 保留原记录。
5. **交付：**Bot 在获准本机目录生成方案，线程先显示待归档，中央确认 v1 后提交。负责人从部门待验收直接打开同一版本，退回形成 v2；验收 v2 后首页、任务看板、成果引用同步，v1 记录不改写。
6. **沉淀与复用：**员工纠正平台任务中的事实或提交归档资产的新版本，保留原版和差异；把可复用方法提为 skill 候选。外部知识服务的条件更新在后期 KD 验收后启用，不作首版退出条件。负责人只有兼具材料访问与目标发布权才可评审/发布。同一 Multica 评估任务与业务评审通过后，另一员工的新任务显式使用获准版本；旧运行/旧模板实例不被静默更新。

工作资产属于公司不等于老板/负责人可读全部材料；私密来源不随群、子任务、模板或复盘扩大可见性。本场景不用千川字段，也不依赖复杂 IM、个人 Cloud 或第二套任务引擎。

### 4.3 公司、部门与 Workspace 的四类走查（映射已确认）

按 Ethan 已确认的 [架构 §4.1](ARCHITECTURE.md#41-部门跨部门与敏感资料)“一公司一个 Workspace＋部门/资源授权”走查。以下是应达到的体验，不是原生已经通过；沿 Project/Issue 评论与 Squad，不新增 IM 或第二套工作台。

| 人与场景 | 从入口到交付 | 权限边界 |
|---|---|---|
| 市场部员工甲 | “我的工作”看待办→部门视图看普通任务→创建“活动文案”Issue→@获权 Bot→本人或合格设备执行→原任务回传成果/用量 | 同部非参与者也可读普通明细；可读不等于可改他人任务、指派 Bot 或调用设备。公司 Workspace 切换器不是部门权限 |
| 市场部负责人 | 同一客户端进入负责部门→下目标/建项目→分解任务、组织已有真人/Bot 小队→看阻塞、按权验收 | 不为管部门升 native workspace admin。私密任务和受限附件仍单授；不能通过计数、甘特或 Leader 汇总反推私密内容 |
| 设计部员工乙跨部参与 | 项目有权管理者授乙项目工作权限或仅授“活动海报”任务→乙从“我的工作/跨部门协作”打开同一 Issue→交付并推进原依赖 | 不复制任务，不加入整个市场部；乙不看该部其他任务，其上级不自动获得访问。只读权不能改任务；交付所需评论/编辑/上传等动作另授 |
| 员工与获授同事处理私密工作 | 有权创建者在创建时限定受众→受限任务评论内协作→检查 Bot、资料、宿主和管理人资格→成果保留原受众 | 同项目成员、部门负责人及平台管理员不能凭角色读取。无合格在线设备显示明确等待，不转给空闲无权设备；个人 Chat 不替代多人私密任务 |

项目授权默认包含已有及后续**普通任务**，沿用相同动作范围；敏感任务和独立受限来源始终另授。只授单任务不开放项目整体/父任务/兄弟任务；导航只显示获准信息，不显示受限任务数量或名称。上述项目继承已由 Ethan 确认；新入部门读取普通历史的默认仍是架构中的待确认建议，本次不顺带定案。

三处必须连贯：

1. **进度与成果**：看板、流程、甘特、收件箱读取同一获权 Issue。跨权限依赖只交换有权方明确提供的可共享交接状态，不暗中公开原任务；不因 Bot 自报完成跳过归档/验收。
2. **组队与上下文**：Squad 不授资料权，原生 Squad 全区可见，名字/角色描述/指令不可写部门秘密；公共约定与受限项目材料分开。Bot 能读不等于评论受众可读；Leader 的私密来源汇总仍须受限或经过有权发布人确认。
3. **调岗/撤权**：甲调部后，首页、已打开线程、搜索持久索引、旧附件链接和 Bot 后续输入按新权限；原任务/资产不随人迁走。独立项目授权需复核；界面区分访问已阻断、受控副本已清理/离线待清理，公司原件继续保留与接管。

合成走查包含同部非参与者、跨部参与者未获权的上级、普通父任务＋私密子任务、在线但资料资格不合格设备。未适配的索引/通知/导出入口须关闭并停止数据同步，不能只隐藏菜单。具体负例与模块 owner 沿 MC-01/01G，不另增任务系统。

## 5. 权限和私密工作的呈现

首版默认创建“公司工作空间”；普通任务明细默认同部门可见。敏感工作或私密群可显式限定本人或指定小组访问，但仍受公司工作资产保留与授权交接政策管理，这种受限设置不是普通任务的默认值。任务可见不等于其来源群聊天可见。界面必须明确写出这些属性，不使用“管理员永远看不到、离职全部删除”等不真实承诺。

个人隐私不属于公司资产。首版不建设完整个人生活助理空间；用户误放隐私时须有标记、隔离、纠正/删除与衍生索引处理渠道。明确可识别的隐私未处理前不进入知识/skill 提炼。不得声称分类能自动识别一切隐私。

加入群、查看历史消息、查看关联附件、运行 AI、修改任务分别检查权限。已有群新增成员不默认公开全部受限历史；MVP 建议默认只看加入后的消息，历史授权另行显式办理。移除成员后，后续读取和推送立即停止；已经合法看过的内容不宣称可以从其记忆或截图中收回。

平台管理员默认只有管理职责，不自动读取全部业务。Multica 管理角色若无法隔离内容则不能直接发给普通运维；需全内容访问的受限管理员另行授权审计，其余只看脱敏健康信息。

### 5.1 账号开通与设备授权的体验

账号开通时指定部门、岗位/角色、资源范围、AI/工具使用权和费用归属；员工随后绑定获准设备、选择工作目录与浏览器会话。客户端检测并受控准备已批准版本的完整 harness 和工具环境，展示下载/校验/兼容状态；不要求员工自行装 CLI、开终端、提供个人 Key/订阅，不默认复用个人配置和登录。公司连接不可用就提示阻塞，不回退个人计费。客户端明确告知哪些内容将传云模型或公司资产库，不自动扫描整台电脑。

员工保留电脑管理员权限，界面清楚区分“我的电脑权限”与“本次 Agent 获准能力”，显示工作目录/浏览器/工具/资料承载范围和撤销入口；加入公用池不是整机接管。负责人身份不自动带来同事设备控制权；员工可暂停本机工作或收回授权。授权变更后菜单、面板、检索、后台运行与本地能力一并收敛，不能只隐藏按钮。公司模型由管理员配置，普通员工只选择有权使用的模型或 AI，不接触原始 Key。

公用 Bot 无法派发时，按查看者权限显示“设备未授权”“设备管理人无对应资料授权”“能力/容量不足”等原因，不显示对方无权查看的资料名称/内容。换机不静默扩大任何人的资料权。

### 5.2 排队、离线和交接的可见性

同机和跨设备的无冲突任务均可并行，不再默认一台电脑只运行一个任务。仅对真实依赖、冲突资源或容量不足显示等待，并分别解释浏览器锁、模型限额、资源不足与上传积压，不能统称“AI 思考中”；单任务取消不误停无关任务。

员工助手设备离线显示等待本人设备；公用 Agent 未启动任务可自动改选其他合格池节点，安全点接续显示新旧 run 关联，未知旧操作显示待核对。全部设备关机明确等待，不云端代跑；全池不合格或资源绑定无法迁移就显示阻塞，不自动借未授权设备。离线停止新动作，恢复先对账，不能把重新连接等同安全重跑。

文件显示本机生成、待上传、公司已归档的区别。失联设备上未上传内容可能丢失，不能称已保留；换设备或离职通过中央资产/检查点和重新授权接续，不要求员工复制个人会话目录。群卡/面板展示未完任务和待交接缺口；未知旧操作未查清不自动再执行。

### 5.3 任务进度、文件保存与接手分开显示

同一任务卡分业务进度、执行设备/运行状态、公司确认保存点、候选/已验收交付四个维度。显示最近已保存步骤/时间与未同步风险，不只显示 AI 自报百分比；保存成功不是任务已完成。Git/普通文件版本在同一资产界面，员工不用掌握 Git 命令。

接手从最近获授权、完整已确认版本建立新的本地工作区，不覆盖新员工已有文件、不复制原员工登录态。同一个公用 Agent 的另一任务可以直接独立运行，不占用或抢原任务目录。人类编辑用接管/导入版本入口；冲突保留候选并提示，不静默覆盖。规则和离线示例见 [任务与工作空间接续](WORKSPACE-CONTINUITY.md)。

## 6. 面板应显示什么

- 员工：我的工作 + 本部门普通任务明细与业务流转；另可查看获授权跨部门项目/任务的进度、交接、期限、阻塞与交付，不局限于个人待办。
- 负责人：所负责部门的目标、任务流转、未认领工作、阻塞、交付、协作依赖和能力维护责任；默认无其他部门全貌。
- 老板：目标进展、部门协作、关键成果与业务指标；下钻仍受资源权限约束。
- 运维：运行故障、队列/同步延迟、模型成本、连接健康；业务内容访问另行授权。

用量面板沿 Multica run 与真实 token/费用回执，企业归集和预算待 B08/C08 验证；员工看本人获权用量，负责人/管理者看授权汇总。任务可读不自动开放他人费用明细；未知价格/待结算明确标注，不记零，token 回传不等于完整金额计价通过。

首版不做按聊天字数、在线时长或 Agent token 数给员工打绩效分。AI 成本与经营预算分开，任务完成与经营指标达成分开。

### 6.1 面板的默认可见范围

面板是各角色的共同能力，不是老板专属。部门范围决定默认工作视野，角色决定允许的操作，资源权限决定能否打开具体内容；三者不能互相替代。

| 身份 | 默认业务范围 | 不能因此获得的权限 |
|---|---|---|
| 老板/公司管理角色 | 公司及各部门的经营与工作总览 | 个人隐私、受限内容的无条件访问 |
| 部门负责人 | 明确由其负责的部门；多部门负责人只覆盖已授予管理范围 | 其他部门完整业务、受限私聊或资产的自动访问 |
| 员工 | 我的工作 + 本部门普通任务的明细与业务流转，默认同部门可见 | 全公司或其他部门面板，以及未单独授权的敏感内容和私密群 |
| 跨部门协作参与者 | 获授权项目或任务的明细及对应业务流转，包括进度、交接、阻塞和交付 | 对方部门其他任务、群记录与资产；其直属负责人也不会自动继承该跨部门授权 |
| AI | 当前任务与委托身份允许的范围，输出还受接收方权限限制 | 因服务账号或所在群而取得全公司知识 |

**已确认规则：部门内普通任务的明细默认同部门可见，不要求逐个任务单独邀请，也不局限于任务参与者。**明细包括非敏感的任务说明、责任人、期限、进度、交接记录与交付信息。敏感内容、私密群及受限附件/资产仍需单独授权；将其关联到普通任务不会解除原有访问限制。默认可查看不等于默认可编辑、分派、发布或管理。

**跨部门授权必须同时覆盖相应的协作可见性，而不只是给一个任务结果链接。**项目级授权可查看授权项目范围内普通任务及其业务流转；任务级授权只覆盖指定任务及授权的交接信息。敏感内容和私密群仍单独授权，不因项目共享自动开放。

对应业务流转至少展示授权范围内的当前阶段、责任人、进度、前后交接、期限、阻塞和交付。跨部门视图与任务卡使用同一权威状态，不另建一套可写状态。跨出授权范围的依赖不自动展开；可由有权人员在共享任务内提供最小必要的交接状态，但不能暴露未授权任务名称、明细或私密群记录。

跨部门协作不开放对方整个部门。授权范围、来源与期限可查，撤销后后续查询、导出、AI 检索和推送都失效。

面板统计、筛选、计数、导出、下载和 AI 摘要同样受权限约束；无权内容不得通过数量或汇总反推。后端先检查部门与资源范围，不能只在前端隐藏菜单。这里的“业务流转”指目标、任务和交接状态，不代表恢复建设工作流引擎。

## 7. 三个不变的体验要求

1. 只需要一个日常入口；不能在聊天里显示完成、任务台却仍执行中且没有同步提示。
2. 结果可追溯到任务、证据、实际执行者与能力版本；模型口头声称完成不算结果。
3. 替换员工、AI 模型或未来外部工具，不应改变公司的任务和资产身份。
