## 3. 缺陷与观察

**F-1（P2，新）项目部门没有手工写入口 — 创建路径已修（2026-11-20 00:25）**
`CreateProjectRequest` / `UpdateProjectRequest` 都没有 `department_id` 字段，`POST /api/projects`
带着 `department_id` 会被静默忽略（§S2-X 取证：201，但库里是 `null`）。目前部门只能由
`FF_DEPARTMENT_DEFAULT_SCOPE=1` 在创建时自动写入。后果：开关默认关时，项目部门标签、按部门过滤项目、
调岗同步部门项目成员（S2-14/16/15）都**没有可用素材**。

已修（创建路径）：
- `server/internal/handler/project.go`：`CreateProjectRequest` 增加可选 `department_id`；校验 UUID +
  本 workspace 存在（不存在 → 400 `department not found in this workspace`）；显式值**优先于**
  `department_default_scope` 的推断；只写归属，不改可见性。
- `packages/core/types/project.ts`：`CreateProjectRequest.department_id` 同步。
- `server/internal/handler/project_department_test.go`：三条回归（显式落部门 / 优先于开关 / 未知或坏 id 400 且不建行）。
- 验证：`go build ./...` 干净；三条测试 pass；实机 `POST /api/projects {department_id: 人事}` → 201 且
  `department_id` 落库、`visibility` 仍为 `workspace`；未知 id → 400。

未修（改归属）：`UpdateProjectRequest` 与 `UpdateProject` SQL 仍没有 `department_id`，改归属需要
新增 SQL 参数并重跑 sqlc（`make sqlc`），单独排期。

**F-2（P3，观察）登录页重复请求 `/api/me`**
`/login` 无 token 时对 `/api/me` 发了两次 401（`rid` 不同，同一毫秒）。不影响功能，可作为启动路径的
小优化项。

**F-3（P2，既有）本机 `make` 缺失 → `scripts/dev-env.sh` 启组件失败**（本轮仍用手工等价命令，见计划 §2.1）。

**F-4（P2，既有）capability 只在服务端强制**：本轮只验了 API 层；前端入口是否隐藏留到 S4。

## 6. Supabase 登录 + 邀请即开户（2026-11-20 补测）

**背景**：客户端密码登录走 Supabase（`POST /auth/v1/token?grant_type=password`），服务端只做
token 校验并换发本地会话；邀请此前只写 `workspace_invitation`，账号要等被邀请人自己在 Supabase 注册。

**已实现（`invite → Supabase 开户`）**

| 改动 | 位置 |
| --- | --- |
| service_role 客户端 + 邀请开户（`POST /auth/v1/invite`，已存在账号视为成功） | `server/internal/supabaseauth/admin.go` |
| 邀请后置开户，失败不阻塞邀请；`provision_state/error/provisioned_at` 落库 | `server/migrations/853_invitation_provisioning.*`、`handler/invitation.go: provisionInvitation` |
| 管理员重试接口 `POST /api/workspaces/{id}/invitations/{invitationId}/provision` | `handler/invitation.go: ProvisionInvitation` + `router.go` |
| 响应新增 `provision_state` / `provision_error`（加字段、可选） | `InvitationResponse` |
| sqlc 重生成（只动 `invitation.sql.go`、`models.go`） | `make sqlc` 等价命令 |
| 回归测试 6 条（成功 / 已存在 / 失败仍保留邀请 / 未配置 / 重试 / 未配置重试） | `handler/invitation_provisioning_test.go` |

**实机验证**

| 场景 | 结果 |
| --- | --- |
| `GET /auth/v1/admin/users`（service key） | 200 |
| admin 建/删确认用户 | 200 / 200 |
| 邀请一个 Supabase 里已存在的邮箱 | `201`，`provision_state=already_exists`，`provision_error` 为空 |
| 邀请新邮箱（`@morechat.co`） | 先通过邮箱校验，随后 `429 over_email_send_rate_limit` → 记为 `failed`，邀请仍为 `pending` |
| 邀请 `@example.com` | Supabase 判定 `email_address_invalid`（该项目的邮箱校验）→ 记为 `failed` |

**结论与遗留**

1. 代注册链路已通：管理员发邀请即尝试在 Supabase 建账号，被邀请人点 Supabase 的"设置密码"邮件即可登录；管理员全程不接触密码。
2. **生产可用的前提是 Supabase 项目配好自定义 SMTP**：默认 SMTP 有严格发信频率（本次直接吃到 429），邀请一多就全变 `failed`（仍可重试）。
3. 若不想依赖 Supabase 的邮件，可改为"admin 建确认用户 + `generate_link` 取 action_link + 用我们自己的 EmailService 发"——需要再加一段，本次未做。
4. 密钥目前只存在本机 `.env`（gitignored），代码不接受非 `sb_secret_` 前缀、只接受固定项目 URL；service_role 一旦在聊天/截图里出现过，建议在 Supabase 后台轮换。

## 9. 预设（Presets）与 Skills 的关系（2026-11-20 14:1x，读码结论）

**不是重复功能，是两层东西：预设是"装配模板"，Skill 是"装配出来的能力单元"。**

| | 预设 `/presets` | Skill `/skills` |
| --- | --- | --- |
| 数据来源 | 内容仓库的 package（`GET /api/presets/catalog` + `/content?path=`），本地无表 | 工作区表 `skill` + `skill_file` + `skill_version` |
| 粒度 | `kind = agent` 或 `team`（`views/presets/lib/kinds.ts`） | 单个能力：说明 + `references/` 文件树，可版本化 |
| 作用 | 一次性装配：建 skill(s) → 建 agent(s) 并绑定 → 建 squad + 生成指令文本 | 被 agent 绑定、被 squad 复用；也可单独创建/从 CLI 导入 |
| 服务端 | **没有 import 端点**，由前端 `views/presets/lib/import-runtime.ts` 编排三/四步 REST | 有完整 CRUD（`POST /api/skills`、`PUT /api/skills/:id`…） |

**安装后的 skill 会不会进 `/skills`？会，而且是同一条记录。**
`import-runtime` 先 `listSkills()`（`GET /api/skills`）按**名字**找同名技能：命中就 `PUT` 更新，
没有才 `POST` 新建。所以装完立刻出现在 Skills 页，同时被 agent 绑定。

**由此带出的两个产品事实（需要决策）：**

1. **Skill 是幂等的，Agent/Squad 不是**：技能按名字 upsert，但 `createAgent` / `createSquad`
   没有同名匹配——**重复导入同一个预设会再建一套 agent 和 squad**，只是 skill 不会重复。
