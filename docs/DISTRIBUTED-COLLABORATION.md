# 群内 Agent 协作与授权设备池

> 2026-11-05，设计评审稿。Ethan 已确认：员工助手默认在自己的授权设备运行；部门公用 Agent 在预先授权的设备池内自动选择；入群不授予电脑使用权；跨设备和同设备均允许资源范围内并行。撤回每台设备默认只运行一个任务的限制。以下为设计契约与可证伪门槛，尚未完成运行验证。

## 1. 目标与方案取舍

平台服务多部门、多员工的人机协作：先决定谁负责什么，再决定在哪里执行。群负责沟通，任务承载责任与交付，设备提供执行能力，三者不是一一绑定。

| 路线 | 取舍 | 结论 |
|---|---|---|
| 群主/发消息人的电脑统一执行所有 AI | 设备成为瓶颈，身份/权限混淆 | 不采用 |
| 所有 Agent 固定一台设备，其他设备只能等 | 简单但削弱公用 Agent 的可用性与并行 | 仅员工助手保留默认本人设备，不作为公用 Agent 规则 |
| 员工助手默认本人设备，部门公用 Agent 自动选授权池 | 协作身份稳定，执行位置可控；需要派发、防重、隔离和离线接续 | 已确认 |
| 自动借用任意群成员/空闲员工电脑 | 容量方便，但不满足授权与数据边界 | 不采用；入群不等于加入执行池 |

中央协作控制＋员工本地完整 harness＋云端模型不变。公司 Key 留在中央模型访问服务，任务/run/成本事实复用 Paperclip；不建设每人一套公司后台，不恢复中央 harness 默认代跑，不引入工作流画布。

## 2. 谁的 Agent 在谁的电脑执行

本文技术用语 Agent 对应产品中的 Bot（AI 同事）。正式 Bot 实例有稳定身份，模板只给配方，小队只建立成员/分工关系；task/run/attempt 描述工作与执行，不产生新 Bot。员工助手 Bot、公用 Bot 的宿主规则如下，不因同一模板、同群或升级版本而授予设备权限。

| 对象 | 含义与规则 |
|---|---|
| 公司 Agent 身份 | 稳定 Agent ID、职责、指令/skill、维护人、可使用范围；不是某个 CLI 进程 |
| 员工工作助手 | 关联员工维护/使用关系；默认路由其指定本人授权设备。别人有权请求助手，也不因此获得该员工电脑控制权 |
| 部门公用 Agent | 部门维护的公司 AI；绑定授权设备池，由中央自动选符合条件的设备。不是在每台电脑复制独立身份或任务库 |
| 运行会话 | 某个任务的一次执行，记录 Agent、发起/委托身份、任务/run、输入版本、设备、派发尝试、租约及费用归属 |
| 设备/runtime | 员工电脑上的受控完整 harness 与工具环境；同一设备可承载多个隔离运行，不拥有任务/资产权威 |

Agent 的维护人、请求人、费用承担方、执行设备管理人可能不同，必须分别记录。工作助手的公司工作资产仍属公司，离职可移交；个人隐私不进入公司交接。

首版员工助手不自动借用部门池或同事电脑。其本人另有设备或需要改变执行位置时，走明确授权的设备绑定/转移；不是跟随“谁 @ 了它”改变宿主。部门公用 Agent 则已获准在其池内自动选择，不要求每次选择重新人工批准，但每次仍须校验当前权限。

## 3. 设备池授权和选择

### 3.1 员工管理电脑，平台只管理 Agent 的授权

**已确认前提：员工拥有自己电脑的管理员权限；morchat 不接管整台电脑。**不以移交管理员权、加入整机管理或禁止员工正常安装软件作为首版前提。反过来，员工的管理员身份、应用登录或入群也不授予 Agent 同等权限。只靠 prompt 限制任意代码不满足目标，仍须验证受限执行边界。

入池记录公司、设备与管理责任人、部门/用途、可运行 Agent、允许请求/委托范围、工具/目录/网络、可承载资料范围、资源配额/可用时段、有效期与授权版本。设备使用同意和公司资料授权分别取得；员工能同意自己的电脑参与，但不能因此授权它承载本人无权接触的公司资料。

**公用 Bot 的准入是交集，不是借用宿主全部权限：**

- 请求/委托人有权发起该任务，Bot 有本次任务及资料使用权；
- 设备在该 Bot 的授权池内，具备有效执行授权及对应资料承载资格；
- 设备管理人对即将进入该设备的资料同样有对应授权；
- 本次运行的工具/目录/会话/网络/模型外发策略允许，且实际隔离与容量满足要求。

四项同时成立才比较负载。管理人有资料权限不等于 Bot 有使用权；Bot 有权限也不等于任何员工设备都合格。同部门普通任务可读不自动开放敏感附件、私密群或对应电脑。设备管理员与公司/部门角色分开，不把“本机管理员”映射成 Paperclip Board 或企业管理权限。

### 3.1.1 本地权限与信任边界

正常运行时，Agent/harness 和工具不得继承员工的管理员执行权限或全部个人环境；仅获本次明确批准的能力。引擎、Python/Node、文件工具、插件及浏览器入口均受实际边界约束，不只检查 shell。安装或修复若确有需要，一次性系统授权须独立说明用途和影响；不转化为每次运行提权，也不开放任意提权工具。员工能暂停/退出本机执行，不影响其他合格节点继续工作。

权限对象是指定工作目录、独立工作浏览器会话、工具和网络等，不是整盘、个人默认浏览器、密码库或系统设置。首版不新增全盘扫描、远程桌面接管、全机软件/账号管制、远程擦盘或 MDM 前置依赖。自动保存仍只覆盖已获准工作内容，不能借公司资产沉淀收集个人文件。

防护目标覆盖 Agent 误操作、提示注入和受限运行中的恶意工具代码；**不承诺抵御本机管理员主动修改/替换 runtime、调试进程、复制已获准落地数据或破坏本机文件。**宿主有管理员身份本身不是违规或禁止入池的理由，但资料必须先满足人和设备双授权。已确认的公司保存点由中央保留，本机删除不能删除公司副本；未上传内容仍可能丢失，不假称已保存。

中央独立检查当前资源授权、运行/设备范围、租约代次、模型额度与权威提交，不以本机“已授权/已停止”的自报替代。设备注册、签名或摘要检查不等于证明管理员从未篡改主机；短期令牌也不保证对本机管理员不可提取，但只能在中央授予的范围和有效期内使用，不包含供应商原始 Key。发现版本/协议异常、撤销或无法验证的停止证据时，拒绝相关新动作并核对，不能自动当作 R2 可信终止。

### 3.1.2 资格贯穿资料进入与恢复

首次派发、下发上下文/资产/保存点、获取工具数据及浏览器资料、恢复旧 session、换机接续时均重验双授权。资料范围变大、转为敏感、管理人调岗/离职或设备授权失效时，先停止继续交付该范围资料及相关新动作，再按既有协议停止/对账；不能先把资料放上电脑，再靠群消息过滤补救。

设备管理人由绑定/入池流程明确记录；多人实际管理的共享电脑必须声明相应管理边界并检查其资料授权，不能仅填一位“名义 owner”忽略其他管理员。无法确认管理边界或资料资格的节点不接对应任务；不因此扫描全机账号。管理关系变化应更新登记；登记不是整机审计或可信证明，不保证识别管理员主动隐瞒/新增的管理者，发现不一致则暂停相关节点资格并核对。具体登记字段与变更通知方式仍属 C01/C06 待冻结接口。

合格设备集合为空时，显示“没有符合资料授权的执行设备”并等待；不自动给员工扩权、不转中央 harness、不擅自把敏感任务派给空闲电脑。存在另一合格节点且满足 R1/R2 接续条件则自动接续，不增加每次人工批准。无合格设备的正确等待不是全局排队策略。

### 3.2 先筛资格，再比较负载

1. 先选业务承接者：人、员工助手或部门公用 Agent，而非先找一台空电脑。
2. 对公用 Agent，只枚举其当前授权池；检查公司、请求/委托人、Agent、任务资源与输出受众。
3. 检查设备在线、运行环境符合要求、授权版本/有效期、设备与管理人的资料双授权、harness/skill/工具兼容、本地资源绑定及执行/模型容量。管理员身份不是设备不合格的替代判据。
4. 在全部合格设备中按可用容量、数据就近性、资源冲突和公平性选取；具体权重由 P0 确定，不改变资格条件。中央选择后设备仍重新验权和原子预留资源，拒收时重新筛选，不相信过期负载信息。
5. 保存选中设备、理由、授权版本、预留与租约；任务卡按权限显示实际执行位置和等待原因。必要信息可见，不公开无权查看的全公司设备清单。

若任务需要某台电脑特有的浏览器会话或未归档本地文件，则它是资源绑定任务，不能随意换到池内另一台。可由有权人员把允许共享的资料归档，或拆成资源所属设备执行的获授权子任务再回传成果；不复制 Cookie/个人登录，不远程暴露 shell 来假装迁移。无合格设备就显示原因并等待，不能扩大设备池或转中央执行。

## 4. 群内多个 Agent 如何协作

群包含真实人员和逻辑 Agent 成员。邀请 AI 的权限、向它派单的权限、被委托资源权限、目标设备执行权限分别检查。群消息不是无限广播执行指令。

- 已确认采用同一输入框 @ 选中具体 Bot 后直接发送，不再设置“普通讨论 / 让 Bot 处理”模式。普通讨论只作为消息；有效的执行型 @ 随发送提交结构化目标，验权后产生或关联真实任务/run。一次针对某 AI 的派单不会让每个群成员设备各跑一遍。
- 给多个 AI 的明确协作请求，拆成可追踪的独立子任务；没有指定承接者时进入待认领/待分派，由获授权的人或被明确委托的协调 Agent 处理，不让所有 AI 抢答开跑。
- AI→AI 交接创建带 parent task/run、目标 Agent、输入资产版本、输出要求、授权范围和防重标识的请求；接手者重新验权。接收/送达不等于推理完成或成果交付。
- 普通 Agent 回复只发布，不产生新的 Agent 唤醒；明确委派和约定的结果就绪/需输入事件才定向触发。显示、上下文消费和执行触发分别授权，不以任意正文字符串中的名字或 @ 自动派工；真人编辑器选中的有效 Bot 提及才随发送形成明确意图，规则见 §4.2–4.5。
- 决策/消息、执行、成果回传分开处理。长任务不应堵住群消息、派单接收、取消与状态通信；进度可合并，审计/计量/交接不可静默丢。忙碌 Agent 可先由系统确认收件，不承诺它立即推理回复或强制打断当前会话。

业务接力另需 task ID、接收方、输入/产物资产版本、待办和验收要求，显示已送达/已承接/缺权限或资料；派单成功、发消息或 AI 自检不算验收。同一已确认委派意图的 @ 与派单共用防重标识，只产生一次有效唤醒，接收方授权在入站和读取时重验。小队模板只映射角色/原生蓝图，实例记录真实成员/版本，不创建第二任务权威；流程见 [完整产品闭环](D:/dev/morchat.co/docs/PRODUCT-LIFECYCLE.md)。

### 4.1 共享上下文，不共享全部记忆

中央按当前授权组装上下文包：必要群消息及可读历史范围、目标/任务/依赖版本、已获授权阶段成果/公司资产、Bot 配置 revision、指令内容快照、skill 版本、来源、权限版本与事件游标。不是把整群历史、所有成员私人文件、其他群或各自完整模型会话拼接上传。

快照后发生的新决策以带版本的增量通知/检查点续跑处理，不能假设所有运行瞬时看到同一段记忆。关键交付前复核目标、输入和授权版本；过期成果可保留证据，但需标记过期并重新核对，不覆盖新决策。撤销后停止后续读取/输出；无法收回已发给云模型或已合法获取的内容。

同一个公用 Agent 可在不同任务/设备上并行，必须按任务/run 隔离模型会话、可变工作区、临时文件与输出；设备也可同时运行不同 Agent。Agent 身份相同不等于共用一份可变 session。共享知识/skill 的修改是版本化候选/发布，不能让并行运行覆盖同一段“全局记忆”。

模型可读与群内可投递分开检查。敏感来源派生内容继承限制；普通部门任务默认可读不解除私密群或附件限制。需要多台设备的信息通过授权子任务与中央资产版本交接，不直接读取对方硬盘。

### 4.2 各 Bot 回复可见，消息不是执行总线

已确认：各正式 Bot 对获授权受众的回复须独立署名、保留原文与任务/run 关联；负责 Bot 的汇总是额外交付，不覆盖成员回复。不公开隐藏推理、秘密或未经授权工具输出；临时子 Agent 的活动归属于发起 Bot/run，不能伪造为新公司同事。

三种流必须分开：①人可看的持久消息；②某次运行可消费的授权上下文；③经授权的派工/继续执行意图。显示给人不等于把消息塞进所有 Bot 的上下文，更不等于全部启动。群主时间线、任务线程、执行详情的呈现以 [体验 §3.2](D:/dev/morchat.co/docs/PRODUCT-EXPERIENCE.md) 为准。

任务线程是围绕原生 task ID 的讨论入口，不是第二种任务。群消息仍由 morchat 保存；已有 Paperclip 评论/运行事件只按原生 ID 投影，不复制为另一份可编辑正文。线程关联群与任务，显示每条记录自己的来源和受众：能看部门任务不意味着能看私密群；同任务出现在多个群，不得自动互相镜像全文。任务详情可聚合有权线程，但不自动形成全体参与者的混合对话。群内线程沿用当前群的授权策略；从首页/面板首次发言须明确选择已授权线程或新建的任务讨论域，并显示受众，未选择不发送；回复沿用该线程当前受众，不由入口猜测。任务讨论域可按普通任务规则对部门可见，但不把关联的私密来源一并公开。跨范围引用/转发重新检查来源与接收范围；来源或受众无法核验的原生记录默认不展示正文、不扩播、不送模型，需有权者补证，不靠隐藏 UI 防泄露。

### 4.3 定向唤醒矩阵

| 输入/事件 | 谁启动 | 必须避免 |
|---|---|---|
| 人的普通讨论、阅读、表情、仅引用名字 | 无 | 用模型监听所有消息；把每条讨论建任务 |
| 真人在输入框 @ 选中具体 Bot 后发送（无模式选择） | 获准的指定 Bot；关联合适的原生 Bot 任务或创建 Bot 子任务 | 靠正文正则猜目标；同名错派；覆盖原真人承接者；全群设备各执行一次 |
| 明确向小队发起目标 | 已指定的协调者；真人协调则进入其待办，AI 协调才建其 run | 因小队成员可见而唤醒全员；强制 AI leader |
| Bot 的普通回复、进度、系统收件回执 | 无 | 文本 @、收到、谢谢、通知回显导致接龙 |
| Bot 明确提交结构化子任务/交接 | 验权后的指定承接者 | 一个委派既由分配触发，又由评论/提及触发；超委托范围扩编 |
| 已登记依赖的结果就绪/失败/需输入 | 对应等待者；普通进度不唤醒 | 每条工具事件唤醒负责人，或者全群广播执行 |
| 重连补拉、旧消息重放、编辑历史 | 无新的执行；仅对账已有意图 | 把历史投影当新派工；旧消息编辑静默改变执行内容 |

每次委派登记依赖批次、必需子项、等待者/真人兜底责任人及结果版本。汇合依据可核验的终态记录，不要求失败/取消也产生文件；成功但约定的资产未确认仍未就绪，资产被撤权则形成受限/需核对记录，不无限等“结果可读”。文本型子项可用已持久化、显式登记的结果引用，不强制生成文件；普通聊天回复仍不因此成为结果就绪触发。可读结果和不泄密的失败/缺项状态一起交给有权等待者；需补权限/未知效果进入具相应权限的责任人待办，不能按成功交付处理。

批次可合并唤醒，但必须记录已选输入与实际处理的消费界标：仅收件、入队或 native ACK 未知不算消费。负责人正在运行时，当前有效的晚到结果记为待处理；在安全边界输入续接，或本轮结束后按同根限额启动一次后续协调。已取消/完成且未获重开授权、预算不足、无法验权或结果未知时，仅保留有权真人待办，不自动复活执行。失权前已读信息不承诺擦除。原生子任务终态/blocker 唤醒与企业结果事件共用同一逻辑依赖通知；done 不等于文件已确认可读，原生摘要也必须裁剪。

重投使用原意图；同一工作的追问、返工、补料使用新意图但沿用原 root，不因人点击“继续”就清零预算。只有获授权、明确独立的新工作才由中央建立新根，同 task 可关联多个独立工作根但需留理由/关联，不靠改 task 名称判断。ACK 未知先对账旧意图；不能用新意图绕过未知结果，也不能把不同真实工作全部去重。

小队成员、消息发送者和名册昵称不是可信调度身份。中央从真实 actor、委托、任务和现行政策确定目标与 lineage；Bot 不得通过另起 root、换线程或伪造父任务逃避同一协作链的限制。

### 4.3.1 @ 是输入方式，稳定目标和权限仍由服务端确认

**确认的交互：**一个输入框、一个发送按钮；输入 @ 出现有权 Bot 候选，选中后形成可删除的提及对象，提交时携带稳定 Bot ID 与正文关联锚点。客户端可预览目标但不授予执行权。复制/引用/代码块、附件内容、Bot 回复、历史补拉、编辑历史均不能自动产生新执行目标；未解析或同名歧义不能靠后台重猜。候选列表本身按权过滤；改名仍绑定原 ID，Bot 删除/撤权后明确拒绝，不落到另一个同名对象。

**首版最小规则建议：**群/任务讨论中的真人 @ 只通知有权真人，不创建 run；Bot @ 才是执行意图。不提供 @all/@everyone 的批量 AI 执行，不启用 OpenMausBot 的无 @ 默认应答者、自动路由或 Bot 文本 @ 接龙。多人 @ 多 Bot 可保留有限多个明确目标，数量上限沿 G0 根链/准入参数冻结，不为此恢复群广播。专属单 Bot 对话可把已明确展示的唯一对象作为绑定目标直接发送，无需每条再 @；这是唯一目标的对话命令，不是群普通消息自动唤醒，目标同样可见、受控并绑定真实任务。不能把多人/多 Bot 群当这种单目标例外。

**任务归属：**Paperclip issue 的真人/Agent 主承接者互斥，不因 @ 把原真人任务改派给 Bot。若当前工作已有同一目标 Bot 承接、同输入/受众范围且可继续的原生任务，新增意图沿该任务与原 root；否则为目标创建真正的原生 Bot 子任务，在已有真人任务下保留 parentId。无任务的群请求建立可见轻量真实工作关联。多 Bot 各有自己的原生任务/派发键，共享来源消息、父工作/root，不让多个 Bot 争写同一 assignee；回复线程可在获授权父工作中按来源关联展示。不得仅凭“同一个 Bot”复用其别的工作会话。

**消息与派工分别回执：**消息可先显示公司已收到；派工另显示目标及“受理中/已受理/拒绝/待核对”。中央校验真实发送者、当前群/线程受众、提及锚点、目标调用权、任务/资料和模型/设备准入。明显有非法目标时不静默执行剩余目标；准入结果须明确。跨多个 Paperclip 创建/派发并非原子事务，部分已提交就逐目标报告已受理/失败/未知，不伪称整批回滚；未知先对账，重试沿原意图。消息 ID/修订、目标 ID 与意图共同防重；删除消息不撤销已经执行的副作用，停止走独立已授权命令。

原生 createChild 的幂等返回不等于 assignment wake 幂等。一次 @ 委派选定一条原生派发路径；创建/分配、评论、企业结果通知等共享原意图回执。普通群消息不逐条镜像原生评论；原生 agent:// 提及可能影响访问授权，不能把普通引用自动转成这种原生授权入口。具体事实证据和适配切点见 [前端依赖审计](D:/dev/morchat.co/docs/REFERENCE-REUSE.md)。

### 4.4 防重、回传与 Paperclip 单一权威

C02 冻结消息与命令关联，C06 冻结派发/设备尝试；不新建任务状态机。至少定义公司/会话/线程、消息 ID/修订、真实发言者、原生 task/run、attempt/epoch、根协作意图、因果父事件、委派意图 ID、来源及受众/政策 revision、事件游标、依赖批次/必需子项/结果版本与实际消费界标。字段名和 schema 在 G0 签认，不能由前后端各起一套。

- **消息可靠发布：**本机先产生有界待回传事件；中央验权、持久化后才能显示“团队已收到”。本机已显示、公司已确认、派工已受理、结果已验收分别呈现。恢复从持久游标补拉；按稳定事件 ID/修订去重，乱序不回退新状态。不同 Bot 的相同文字不能按文本误删。
- **派工可靠受理：**消息/意图持久化与调用 Paperclip 之间允许存在故障窗口，须有可恢复的命令回执/投递记录。超时先查原生结果，再用同一意图防重重试；不能新建另一任务掩盖未知结果。这些记录仅记投递/确认，不持有第二份承接与完成状态。
- **单次执行触发：**同一委派意图经按钮、评论投影、分配事件、重连和多消费者到达，只能产生一次有效原生派发；合法重试/接续仍有独立 attempt。Paperclip 原生普通评论（含 update 携带 comment）、mention、分配、子任务终态和 blocker 唤醒入口也须纳入同一企业准入/防重或关闭不使用的自动路径，不能只在聊天前端去重。
- **停止与迟到：**取消或撤权后的事件可按既有证据权限留作审计/费用对账，但不得再唤醒 Agent、复活执行权或伪称当前交付。权限撤销同时覆盖后续推送、补拉、搜索、上下文和附件；已合法落地的副本不承诺远程抹除。
- **输出与控制分离：**普通进度只更新原任务活动卡；审批、阻塞、失败、停止、正式交付及审计/费用回执不能静默丢失。低优先级积压不得堵取消/撤权/收件；触发新的 AI 汇总也必须是可追溯、受预算约束的真实 run。

### 4.5 防风暴不是全局串行或只靠提示词

执行层必须对同一根协作链持久累计：单次派工扇出、委派深度、总有效唤醒/自动继续次数和模型费用；传输层另限消息速率、载荷及积压。重启、换设备、换线程、阶段有进展不能自动清零总预算。费用以 C08 准入/在途容差为准，不把事后账单当硬停证明；安全重试也计真实调用。有限配额下不同任务仍允许并行。

触顶停止受限的后续自动动作，保留已知结果，生成一条可见的限制原因与有权人的处理入口；恢复/追加预算是可审计的授权操作，不由 Bot 自批。停止消息不再触发新一轮模型解释。循环检测只是提前拒绝机制；A→B→A 也可能是合法返工，因此还要验证新意图与已批准次数，不能只靠文本相似度或永久禁止回边。

具体参数由 C02/C06/C08 owner 在 G0 对同一 fixture 签认：扇出、深度、根链总次数/费用、并发在途容差、消息/积压上限、控制响应与投影恢复时限。未填值即 BLOCKED，不可称“已防风暴”；这些不是全公司总任务上限。反例唯一清单见 [Discovery §4.4 MSG-01–08](D:/dev/morchat.co/docs/DISCOVERY-BASELINE.md)，不另造测试框架。

### 4.6 追问、批准、补充与停止：原生状态，企业授权，本地执行

这是完整人机操作的唯一命令语义，展示见体验 §3.5，固定源码证据见复用 §4.5。继续遵守 @ 定向派工：专用回答/批准/修改队列/停止按钮是在已确定任务与对象上的命令，不需补一个 @；普通群消息、改旧消息或 Bot 输出不变成控制指令。

1. **唯一记录与关联。**复用 Paperclip 原生 interaction/approval/queued-comment/run 及其事务、修订和投递 outbox。C02 冻结每种操作对应的原生对象类型，不把问题、工具许可、治理审批、成果验收混成万能 approval。B06 仅补跨设备投递关联/回执；若 ACP 工具请求缺合适原生持久对象，由 Paperclip owner 评审最小扩展，不能并建审批引擎。
2. **请求和消费分别确认。**关联 company/task、interaction 或 approval ID、原请求/原 run、attempt/epoch、actor/目标 Bot、有效期、policy revision、必要的内容/工具参数摘要及幂等标识。队列另带 queueId/item ID/revision/targetRunId；沿用真实原生字段，未冻结字段不伪称现成 API。服务端重验当前回答/决策权及来源限制，不能以部门职务或群成员身份代替。跨窗口重复提交只得到原决策或明确冲突；答案持久化、投递、harness 消费是不同事实。
3. **迟到与重启。**原本地问答/许可回调失效，保留中央工作事实；不得向新 run 的碰巧同号请求投答案。已终结/已撤销请求不续跑；仍有效的工作通过原生投递对账和当前授权决定是否重新提问/建立有来源的接续 run。需真人回答必须结构化标识，不按中文/英文自然语言猜测，也不让上级 Bot/default 悄悄代答。取消/过期后回执仍可记审计，不恢复执行权。
4. **补充必须是新意图。**@ 追加并关联已有工作，若准入为本次执行补充，则进入唯一 native queued-comments 路径；任务分配、评论镜像不得再唤醒一遍。未消费允许按原生 revision 改/撤；已消费不能编辑过去，只发新补充。队列 ACK 丢失先对账，不重投第二条。原生队列是等待目标任务安全消费的输入，不是把跨设备独立任务全局排队。
5. **能力决定送达方式。**即时 steer 只对已探测支持且原 turn 仍匹配的运行开放。DSH remote 首版可用下一安全轮消费；“停止并按新要求继续”是显式 interrupt 意图，须可信终止/效果对账后执行。unsupported/暂不可用/已消费/交付未知分别可见；入队不标已注入，超时不盲重试。
6. **停止有明确范围。**“停止本次运行”只取消选定 native run，展示相关仍活跃子项；“停止本次协作”针对当前 root，先阻止新增派发/委派、结果触发及待处理输入消费，再按有权范围调用现有 run 取消、聚合设备回执。只有具该任务/root 管理权并能核查所涉内容的人可控制；部分无权或未知不报整组成功。不能停同 Bot 的其他 root，也不能通过换设备绕过停止。
7. **停止不自动继续。**原有补充保留审计但不自动排空，迟到子任务结果/重连不启动新工作。新获授权的明确“继续”记录新意图，仍沿原 root 配额/版本和未知效果核对，不能清零预算。普通停止不得接到 native queued-comments/interrupt。已批准动作也需检查当前取消/租约/政策；已发生效果只记录/核对，不倒带。
8. **停止回执不作假。**区分控制请求已接受、执行器已收到、真实已停止、效果待核对；离线时保持未确认并撤新准入。原生取消撤提交权不等于物理进程已死；真实停止、撤权截止与副作用按 §6.4 及既有 DV 参数验收。保留费用和迟到证据，不允许重连重放或无界等待吞掉人工待办。

P1 包含上述最小控制链和 root 范围聚合，不包括批量跨 root 控制、群 hold 或文本猜 stop/resume。并发、控制优先和资源释放按既有契约，不能为实现卡片新增一个调度/队列权威。OP-01–04 是对应 P0 子样本。

## 5. 并行执行和仅在必要时等待

已确认：跨设备默认并行，同设备对无冲突任务也允许并行；撤回每设备默认一个活跃任务/执行链的设计。不是无限并发，容量按实测分资源设定。

| 范围 | 规则 |
|---|---|
| 多部门/多设备 | 各自推进独立任务，不能因另一个部门或设备忙而全局串行 |
| 同一设备 | 独立会话/目录/资源的任务可同时运行；子 Agent、不同客户端实例均计入该设备真实配额 |
| 共享 Agent | 不同任务可用独立运行并行；同一派单/同一任务尝试只能有一个当前有效领取，防重不是禁止不同任务并行 |
| 冲突资源 | 同一交互桌面、需独占的浏览器会话、同一文件写入等局部互斥；无关任务继续，读/写规则按真实工具验证 |
| 业务依赖 | 只阻塞真正依赖上游的步骤；父任务持久化等待并释放可释放的执行/写锁，子任务不被父任务持锁卡死 |
| 模型/设备容量 | 超出 CPU/内存/进程/IO、模型 RPM/TPM/并发或预算时有限排队、退避/拒绝并解释原因，不把上限固定为全公司或每设备一个 |
| 中央通信/上传 | 有界队列、多执行端并发领取与背压；有队列不等于所有任务串行，执行拥塞不能无界堆积或阻断控制消息 |

在途操作到安全点后保存必要检查点/输入版本并释放锁；不能安全释放则标资源阻塞，不假称资源空闲。续跑重新授权、取锁和检查资源版本。多资源申请要有避免环形等待的规则（如固定顺序或失败回退），P0 选实现并验证。暂停/取消可针对单次运行；设备暂停影响该设备，不误杀其他设备/同机无关任务。系统不从员工正常办公无限抢占资源。

## 6. 离线与自动接续的分界

**可用性范围已确认：**不要求全部员工关机后仍继续执行；全池无合格在线设备时等待是可接受状态，不引入常在线节点或中央 harness 兜底。单台关机不应暂停其他在线成员的独立工作；公用池原有授权选择/安全接续规则不因这项确认取消。任务级暂停/取消与设备离线分开，不能把明确停止任务的指令通过换设备绕过。关机不等于任务完成/取消，也不证明此前的云模型请求或外部动作没有产生效果，仍按以下规则对账。

池内自动选机、重新选择未开始工作、迁移正在执行的工作是三件事。不能拿“自动选机”当作重复执行的许可。

| 情况 | 处理 |
|---|---|
| 员工助手默认设备离线 | 请求仍可持久接收，标等待本人设备；不自动借同群/部门池，其他成员照常工作 |
| 公用 Agent 尚未派发，某池设备离线/无容量 | 自动选另一台符合全部条件的池设备，不要求固定维护人电脑在线 |
| 已发 offer 但可证明未获得启动权限 | 原子撤销/到期并阻止迟到领取，重新选择；设备必须收到中央有效启动租约后才能执行。启动许可已提交而 ACK 丢失属于结果未知，不能当作未开始 |
| 已领取/已运行，设备失联 | 标运行结果待确认，阻止旧租约后续模型调用/权威写入；不能仅凭离线或租约到期就自动重跑 |
| 满足 R1 共享效果隔离/可安全重算，或 R2 可信终止条件；中央恢复边界已对账且无未知项 | 按已授权池策略自动选合格设备，新 attempt/run 接续原任务；恢复边界必须覆盖检查点之后已提交的业务效果，不得重放已完成操作。重验权限，无须逐次批准，不迁移个人登录 |
| 旧进程/工具是否完成未知，或资料只存在失联本机 | 相关任务阻塞核对；有任务管理权和证据访问权的责任人处理，不为保证“永远在线”而重放 |
| 所有合格设备离线，或资源只绑定离线设备 | 明确等待原因；不去未授权设备，也不恢复中央 harness 兜底 |
| 设备/池授权撤销 | 立即停止新派发/领取/模型准入；本地在短租约与安全停止点收敛，测量失联窗口；不得自动再次选入 |

启动与接续均校验授权、task/run/attempt 与递增租约代次；新旧尝试并存期间旧结果不得成为当前任务完成。旧设备仍可信时，可经重新鉴权取得仅旧 run 的证据上传权；被撤销设备旧凭证全部拒收，必要时由获授权接管人恢复导入。迟到真实费用由中央网关/供应商证据对账，不因旧租约失效丢账。

自动安全接续与未知结果人工核对必须在界面区分。未上传产物随失联设备损坏可能丢失，不能把“准备迁移”显示为“已交付”。公司只保证提供已提交归档的版本；资产/Key/权限边界见既有文档。

### 6.1 启动与提交不是同一个防重关口

以公司＋逻辑派单/独立子任务 ID 确定唯一执行范围，attempt/run 是此范围内的尝试，不因重启生成新 ID 就绕过防重。多调度器、同机多个 runtime、重复投递都只能取得同一范围的当前有效启动许可；不同独立任务继续并行。启动许可提交而确认丢失时先查权威领取记录，无法确认就按已可能执行处理。

新旧代次、任务/输入版本和权限的校验必须在提交生效处成立，不只是网络请求发送前。覆盖任务状态/转派、子任务创建、正式资产关联/发布、向群投递；旧证据和真实费用分别走隔离/结算路径，不当成当前业务完成。

- 优先使用权威端可验证的条件写入/版本或 fencing 契约，让过期条件在提交时被拒；P0 必须证明所选 Paperclip/API 路径确实支持，不能假设字段存在就有效。
- 若缺少此类契约，只有在所有相关写入都经过受控单写入口且同一任务/资源的提交顺序可证明时，才评估短提交区间的持久顺序化协议；这不是把 Agent 执行或整个设备串行化。用户转派/取消、Agent、插件和原生台不得绕过此入口。无法约束的写入口首版不开放。
- 跨系统调用超时且可能已提交时，保持该资源的提交结果待确认，不在新代次继续提交冲突命令；先查账/回读确认，不能释放一把进程锁就假定旧请求失效。新运行准入和接续亦受该不确定性阻塞，无关任务仍可执行。用户的取消请求已接收不等于任务取消已生效。
- 不把 morchat 的命令/提交记录变成第二套可写任务状态；Paperclip 仍是任务/run 权威。暂存文件可以存在，但转为已归档/当前关联须通过提交门禁，正式交付还须业务验收；资产正式发布在本域原子检查。群投递按当前受众权限/任务版本检查，检索/下载/读取同样实时授权，不把暂存结果直接推送。

如果既无受支持条件提交，也无法在全部写入口上证明顺序和不确定请求处理，则本候选接入不能通过 P0；不能依靠“先检查＋之后必定成功”或 outbox 去重宣称正确。

### 6.2 自动接续需要可对账的恢复边界

检查点必须包含已覆盖操作序号、输入/上下文版本、已完成步骤/结果引用及未完成项；中央保存逻辑操作 ID 与已提交业务效果/回执的关联。检查点之后完成的子任务创建、资产发布或共享文件写入，也必须先对账并纳入恢复清单，不能从旧检查点无条件重放。

同一业务操作的防重标识跨 attempt 保持关联，实际新的模型请求和重试消耗仍按真实请求分别计费。共享文件写入通过内容/版本和工具回执核对，不能核对则标未知。只有确认哪些应跳过、哪些可安全续做，且符合 R1 的完整效果隔离/安全重算或 R2 的可信终止条件，才建立新的恢复边界并自动接续；否则进入异常核对。

旧执行终止证据需来自受信 runtime 对受管理进程树和工具的退出/收敛确认，以及中央/连接器/资源侧的结果对账；旧租约到期、设备离线或一句模型自报完成都不足以证明。无法观察/终止的外部动作和脱离管理的子进程不能假定消失；失联期间无法证明安全就不自动接续。本轮建议不把物理停止当成所有任务的唯一通路：仅对经验证的 R1 任务，全部共享提交已隔离且可安全重算时允许新尝试；R2 仍需上述终止证据。定义见 [任务与工作空间接续](D:/dev/morchat.co/docs/WORKSPACE-CONTINUITY.md) §6；具体证据由 P0 选择并注入故障验证。

### 6.3 数据与会话授权贯穿运行

池资格不是仅首次选机通过。上下文增量、新资产、下载/截图、工具返回、检查点与旧会话在第一次送达宿主或授予可获取能力之前，必须重验来源权限、数据分类和设备承载资格；不能等模型外发或群投递时才发现宿主无权。

对于会先在本机产生资料的浏览器/工具，授权需限制它能访问的业务账号、资源/站点和预期数据范围；来源敏感性无法预判或无法限制则不向该设备开放该读取能力，而不是先下载再筛选。运行中资料升敏、权限收紧或池撤销时暂停相关读取/执行，撤销后续模型及工具能力；是否换合格设备仍按安全接续规则，不扩权。已合法读取的数据不能保证从失联或受控失败的宿主擦除。

同一 Agent、同一任务或同一设备都不自动允许复用原始 session。新 run、追问身份变化、权限/来源变化和跨设备恢复时，须核验旧 session 所含上下文及能力仍允许；无法证明或 harness 的 resume 绕过中央裁剪时，清除复用路径，用当前获授权上下文重建新会话。其他并行运行不继承本次权限或记忆。

### 6.4 三种停止边界和满载控制通路

中央撤销后先拒绝新的派发/领取/模型请求/权威提交；设备侧的新动作准入依赖可信 runtime、在线状态和未过期短租约；已经在途的模型流、浏览器下载和子进程则需分别取消/收敛与结果核对。短租约不能作为所有在途操作停止的上界，也不能强停已攻陷宿主。休眠恢复、时钟异常和半开连接须重新验证而非延长旧授权；失联检测、准入失效和实际停止的时限分别测试。

控制收件/取消确认与真正停止分别展示。执行、日志、上传或模型请求占满时，控制消息通路的连接、处理能力和持久化等共享瓶颈仍需保留容量/优先级；不是只开两个队列就保证可用。P0 在饱和和断线场景验证收件、状态、单次取消及实际安全停止，具体容量数值先定后测。

### 6.5 中央旧快照恢复不能复活旧执行权

灾备恢复不是普通设备重连。先隔离派发、模型准入和权威提交，并隔离旧中央写入端；不能让新旧控制面同时有效。恢复实例使用不复用的恢复世代/授权校验标识，使备份中的旧租约、凭证和派发许可不能重新变成当前；具体机制由实施设计确定。

恢复期间不直接对员工开放旧成员/ACL 快照。先重建或由有权责任人确认当前账号、设备、撤销和数据授权，再重新鉴权；对账 Paperclip、资产、成本与检查点之后已提交效果，确认无需重做的操作后才恢复派发，无法证明则保持阻塞。恢复还须核对根链已消耗/在途额度、原生派工受理/防重回执、依赖批次和消费界标；不能仅换 epoch 就把旧快照中的余额、未处理标记当当前事实。采用可核验的持久记录重建，无法证明则阻塞该链并交有权人核对，不以默认零计数继续。P3 注入旧快照恢复＋设备仍在线＋旧请求迟到＋已撤销凭证/已执行派单，并覆盖快照后根已触顶/结果已消费，验证不会回拨权限、预算或重放业务。

## 7. 一次跨部门群协作验收

负责人下活动目标，运营员工与内容员工进入同群，加入员工助手和部门公用分析 Agent。运营助手默认本机运行，公用分析 Agent 自动选池内合格设备；内容助手并行起草，不等待全部分析结束。

同一设备还可在独立工作区并行生成另一份文档；若争用同一浏览器会话，只让冲突操作等待。分析阶段结果归档后，经授权输入包交给文案任务补充事实。负责人更新目标时，各运行收到版本变化并在交付前核对。消息与面板不因长执行失去更新。

关闭一个池节点：新任务选另一个合格节点；已运行任务先确定安全接续或未知阻塞，不能重复执行。员工助手自己的电脑离线不会偷偷换宿主。取消任务、撤销入池权限、把敏感资料交给无权 Agent 的尝试均须有可核验拒绝记录。最后成果回同一任务/群，成本与资产归属不因执行设备变化而改变。

## 8. 可证伪门槛与证据状态

这些不是 P3 才补的优化项，而是 P0 必须先验证的架构条件，P1 形成产品切片，P2/P3 扩大权限/故障/负载回归。当前状态统一为“未运行验证”；写出协议或源码存在某字段都不算通过。

| 编号 | 必须提供的证据 | 否决当前候选方案的结果 |
|---|---|---|
| DC-01 | 同群多员工/AI，任务按逻辑 Agent 路由，员工助手默认本人设备 | 按发消息人/群主选机，或入群即可操控别人电脑 |
| DC-02 | 公用 Agent 在至少两台授权设备间选择；设备及管理人均有对应资料授权；初始及运行中数据/来源/授权改变、撤销节点均被排除或暂停，未获准资料首次进入宿主前阻断 | 只能固定一台、选机扩权，或先把资料交给无权宿主再筛选 |
| DC-03 | 同机至少两项无冲突工作真实重叠、跨设备并行、共享 Agent 会话隔离；同任务新 run/不同身份追问/跨设备恢复时旧 session 不绕过当前授权 | 全局/每设备固定单任务，或会话、文件、身份串用/越权恢复 |

### 8.1 本机管理员前提下的验证子样本

复用 DC-02、PC-19、WI-02/06、NG-02 和 DV-08，不增加另一套测试系统。使用合成私密标记，普通 Agent 负例不得让员工先手动改策略或批准提权来“制造越权”。

| 子样本 | 必须观察到 | 判失败 |
|---|---|---|
| 员工账号属于管理员组，Agent 正常启动 | harness/工具仍按受限配置运行；未授权目录、其他 run、个人会话与管理员动作被拒；授权文件/工具正常可用 | 以宿主账号权限直接放行；只有 elevated/unrestricted harness 才能工作；靠提示词自律 |
| 设备有承载授权，管理人无资料权 | 选机排除，正文、附件、保存点或可推断秘密的元数据未送达 | 设备空闲/已入池即可收到资料 |
| 管理人有资料权，设备未授权或 Bot 无权 | 分别拒绝；重新给予合法授权后对应正例才能执行 | 借员工完整权限、公司管理员角色或 Bot 身份绕过缺项 |
| 开跑后新增敏感附件或撤管理人资料权 | 在首次送达该资料或授予获取能力前重新筛选；停相关动作、旧请求不得新获权；换机前重新授权与对账 | 只在开跑时验权；先下载再筛；沿用旧 session/检查点复活授权 |
| A 关机，B 有设备权但管理人无资料权 | 拒绝 B；无其他合格节点则明确等待；给 B 合法双授权并满足接续条件后自动继续 | 为保证 RTO 把资料送给 B、扩权或中央代跑；合法正例却固定等原机 |
| 撤销/疑似 runtime 异常、旧回执迟到 | 中央拒绝无效凭证、旧代次的新访问/提交；不把设备自报停止当可信终止；真实费用继续对账 | 因本地管理员标记/自报绕过中央授权，或未知结果直接自动重做 |

最后一项验证中央边界，不宣称防住管理员主动窃取已落地字节或强制删除其副本；这些不在本机防护承诺内。管理员身份本身不能让节点被一律拒绝，也不能让 Agent 越权被视为可接受。判定依据必须区分正常受限 Agent 行为、已获准在途效果与人为改动主机，记录实际有效权限而非只看账号组名。

P0 在获授权临时验证环境中记录固定版本、设备/资源条件、操作步骤、run/attempt、时间线、权限决策、资产和计量回执；具体性能阈值先确定再测。两个并行任务是最小正确性用例，不是容量上限。Paperclip、适配器和本地 harness 的并发/会话契约都必须测，不能仅模拟中央派发接口。

若失败，先定位是否可通过受支持配置/适配/替换组件解决并复测；失败前不能宣称可行。若只能靠违反已确认边界才能工作，则当前技术组合或架构假设不成立，应暂停后续功能建设、提交问题证据与替代方案重新评审。单个组件失败不等于企业协作方向被永久否定，但不允许用“一律串行、原始 Key 下发、随便借电脑、中央代跑”换一个名义通过。
