# 从目标到团队、交付和持续复用

> 2026-11-06。已确认六步产品主线与 Multica 统一客户端/后台/唯一任务、run、调度底座；中央控制＋Windows 本地 DSH＋云端模型。本文保留产品门槛，字段和实施契约 C01–C08 仍为 DRAFT，未冻结，未验收。

## 1. 产品主线与不变边界

morchat 是公司的人机协作平台，而非 Bot 集合、单人助手或千川工具。公司保留工作成果、方法和可维护的能力，但不保留个人隐私，也不因留存而向全员开放。

同一个客户端提供工作群、我的工作、部门/公司/获授权项目面板、AI 同事和资产目录。员工可发起工作、建群、维护获授权的岗位包/小队模板；负责人使用相同入口，多出实际被授予的目标管理、部门分派和发布权限。老板不是唯一能看面板或下目标的人。

中央是 Multica 协作控制与核心数据服务；模型推理在公司管理的云端，完整 DSH 和工具在授权 Windows 设备。组织助手、岗位检查、复盘和 skill 测试也必须有真实 Multica task/run，走同一本地派发、授权、自动保存和计量链。公司 Key 不下发通用 harness。无合格设备时明确等待，不云端代跑，也不阻止人工建群、认领、验收。

工作流画布、通用流程引擎、Coze/n8n 集成继续暂缓。小队模板是角色和交付的组合配方，不是一套新的低代码系统。语音、自动注册外部账号、发送邮件和生产业务写入不因参考资讯而进入首版。

### 1.1 统一定位：Bot 就是 AI 同事

产品层称 **Bot（AI 同事）**，工程中对应 Multica 的唯一稳定 Agent 身份，不另建影子身份/可写配置，不把真人映射为 Agent。员工助手、部门公用 Bot、组织助手是职责/范围，不是不同运行引擎。

Bot 有稳定身份、职责、维护人、授权范围和能力版本；不是模型、harness、电脑、进程或某一次聊天。一个 Bot 可参与多个获授权小队，执行多项隔离任务；同名不等于同一身份，换设备/升级能力不应新建影子 Bot。模型/工具/电脑权限仍分开管理。

任务内部临时子 Agent 是执行单元，不自动成为名册中的公司 Bot。确需长期复用或独立治理时，再经过已有 Agent 创建/授权流程形成正式 Bot；不能把每次拆分都当扩编。

### 1.2 模板、实例、工作和运行的关系

| 对象 | 定义与关系 | 版本/身份边界 |
|---|---|---|
| Bot 模板 | 创建/受控更新 AI 同事的配方：岗位、配置、指令、skill 与工具需求 | 模板独立版本，优先 Multica 现有载体；缺口按 B03/B04 验证。无成员、设备、凭据、旧记忆或权限 |
| Bot 实例 | 公司名册中的具体 AI 同事，映射唯一 Multica Agent；来自模板或复用已有实例 | 稳定 ID；来源模板与生效能力版本另记，升级不换身份；实际授权另授 |
| 岗位入职包 | 职责、材料、质量要求与就绪检查；可供真人学习，也可被 Bot 模板/实例引用 | 不是另一种 Bot，也不强制每个 Bot 配一份独立副本；正文/材料复用已有载体 |
| 小队模板 | 真人/Bot 角色槽位、能力要求、任务蓝图与交接/验收规则 | 模板版本独立于小队实例；沿 Multica Squad 适配，不导入 TEAM 包后台或第二引擎 |
| 小队实例 | 本次合作的实际真人和 Bot、目标/群/项目关联及确定的模板/能力版本 | 优先绑定已有 Bot，不为每次组队克隆整队；升级模板不改写已组建小队 |
| 任务 | 有输入、产出、承接者与验收要求的工作，唯一事实在 Multica | 任务身份不随设备或重试变化；换承接者需授权与交接 |
| 任务运行 | Bot 执行任务的一次 run；派发/恢复另关联设备 attempt、租约和工作区 | 一个任务可先后有多个 run/attempt；一个 Bot 可并行多个隔离 run；运行固定实际使用的能力和输入版本，不等于新 Bot |

关系主线：**Bot 模板 → 创建/受控更新 Bot 实例；小队模板 → 绑定真人和已有 Bot → 小队实例；任务 → Bot 的 run → 具体设备 attempt。**模板是配方、实例是身份/成员组合、run 是工作过程，三者不能互相替代。技能是 Bot 可复用的方法，不是它的身份或私人记忆。

例如“运营分析 Bot”今天做活动分析、明天做千川只读分析，仍是同一位 AI 同事的不同任务；同一模板可创建不同部门的独立 Bot，但不因来源相同共享权限/会话。

## 2. 六步流程：每一步有真实产物和责任

| 步骤 | 员工/负责人怎么用 | 系统形成什么 | 进入下一步的条件 |
|---|---|---|---|
| ① 提出目标 | 从工作群、我的工作或目标面板填写，或请组织助手用自然语言整理 | 目标简报：预期结果、输入与来源范围、验收标准、期限、业务负责人/验收人、资源/费用约束；关联 Multica 项目/任务；目标关联缺口须适配 | 缺项清单有补充人；未确认范围只作草案，不代表其他部门已承诺投入 |
| ② 组建人和 AI 团队 | 推荐已有同事/AI，选择岗位包或小队模板，查看差异后按权限应用 | 小队实例、角色槽位与真实成员映射、工作群/项目关联、待邀请/待授权/缺能力清单；必要时提出新增 AI | 人员接受或有权分派成立；工具、资料、版本、设备分别通过检查；未就绪角色不能显示可执行 |
| ③ 拆分认领任务 | 查看拆分建议，调整交付物/依赖，认领或按权委派 | Multica 任务/依赖、当前承接者、业务责任、验收人、输入版本与期限 | 认领须服务器原子决定；输入授权与依赖满足；可读不等于可抢他人任务 |
| ④ 协作交付 | 群内跟进、补充资料、交接阶段成果、退回修改或验收 | 任务/run、自动保存点、版本化成果、交接回执、验收记录和实际费用 | 文件获公司持久确认才可提交验收；指定验收人接受才算验收完成；派单/发消息/AI 自检均不算完成 |
| ⑤ 复盘沉淀 | 在已授权任务上点“复盘/改进方法”，指出成功经验或错误 | 知识、岗位包、小队模板或 skill 的改进候选；关联来源证据、基础版本、差异、适用/不适用条件、评估案例 | 先分清项目事实与通用方法；候选经评估及对应发布权检查，不因“做对一次”自动成为公司规则 |
| ⑥ 下次复用 | 在新工作中选择已发布模板/能力，换实际成员和输入 | 新实例、新 task/run；固定模板/岗位包/skill 版本；重新授权后的输入清单；实际加载证据 | 不继承旧会话、旧凭据和旧授权；能力缺失/版本不符显示阻塞，不能偷偷改用 latest；新结果再次回到复盘 |

这里的“草案、准备中、可用”和交接回执只描述方案/组队操作自身，不是另建一份可写任务状态机。任务、执行、保存、验收四类状态按 [工作接续协议](WORKSPACE-CONTINUITY.md) 显示；公司目标的经营结果另有指标，不以任务完成率冒充。

### 2.1 最少责任关系

- **发起人**提出需求；**业务负责人**管理范围、优先级和阻塞；**执行者**承接具体任务，可以是真人或 AI；**验收人**判断是否满足约定。小任务允许同一真人兼任业务负责人/验收人，但必须显式显示，不默认所有任务加第二审批人。
- 每项任务一个当前主承接者，协作者用关联成员/子任务表达，不用两个可写负责人字段争夺权威。AI 承接不消除人类业务责任。
- 真人使用真实 user，AI 使用稳定 Agent ID；业务负责人、执行者、验收人分别表达，不能覆盖底座身份/安全字段。具体扩展与条件认领在 C01/C02 验证，不沿用 Paperclip responsibleUserId 假定。
- 同部门普通任务可读不等于可认领已承接工作、转派、发布、读私密群或使用同事电脑。跨部门邀请/请求协作不等于获得对方部门的派单权。

### 2.2 变化、重试与交接不是异常边角

- 目标/验收标准变化先给出差异和受影响任务，由有权者处理已认领工作的重排；不静默覆盖在途交付约定。
- 组队是一组可恢复操作：每次操作及各步骤有幂等标识、底座对象 ID 和回执。群创建成功、任务失败时显示部分成功，重试只补缺项；不重复造 AI/群/任务，不自动删除已经被他人使用的对象。需要经核验的幂等或可查询确定结果；结果未知先核对，不盲重放。
- 业务交接包含 task ID、接收方、授权输入/产物版本、待办与验收口径，区分已送达、已承接、缺权限/资料。群邀请不公开来源群全部历史；依赖完成也不自动授予输入读取权。
- 同一个任务已通过派单唤醒，就不再因同一条 @ 重复启动；AI 回报不触发无限互聊。跨设备无冲突任务并行，只有依赖、资源冲突、预算或无合格设备才等待。

## 3. 四类能力如何落地

### 3.1 AI 组织助手：可选的组织能力，不是超级管理员

**入口：**“帮我把目标组织起来”“用这个模板组队”“检查小队缺什么”“复盘这次工作”。员工和负责人共用入口，结果受各自授权约束；也可不经助手直接操作表单、群和任务卡。

**首版行为：**澄清少量缺项 → 检索可见且可使用的现有同事/AI/模板 → 提议角色、任务、交接和费用归属 → 展示新增/复用/变更清单 → 依据委托权限执行可执行项，缺权项交给相应授权者 → 显示真实回执/缺项。优先复用，不以新增 Bot 数量为成绩。

该能力体现为 Multica 中的组织助手 Bot 与受控工具；Paperclip create-agent/Reflection Coach 仅作治理机制参考或独立源码候选，不接其后台。每次工作独立 task/run/context，可并行，不成为全公司单一串行进程。关闭助手仍可人工工作。

Multica 原生 Agent Builder 已能通过配置对话生成 Bot 草稿并由用户确认，Duplicate/CLI agent copy 已有；优先复用，不新造设计器。它们不等于完整组织助手或公司模板发布：copy 虽排除 custom_env/mcp_config/runtime_config，却复制调用权限与 allow-list，实例化时必须按当前政策重置或重验，不能继承旧授权。固定源码证据见 [Evose 对读 §7.4](EVOSE-PRODUCT-RESEARCH.md#74-新增源码证据索引)。

“自然语言创建”不授予任命员工、扩大部门权限、读取所有历史、无限创建 AI、开启定时任务或改公司安全策略的权力。有明确授权的动作不必逐步人工二次确认；增加权限/预算或超出委托时才走相应门禁。首版模板例行任务默认不激活，创建逻辑 AI 不代表已有设备可运行。

所有 Bot 创建、模板安装和 API 写入口执行相同公司政策；预览和应用须绑定确定内容与效果清单。无法验证导入入口的发布、权限、幂等和副作用边界时先不开放，不导入参考项目 raw importer，也不让每次合法组队都变管理层审批。

### 3.2 岗位入职包：职责、材料和“确实能工作”的检查

| 内容 | 最小要求 |
|---|---|
| 角色约定 | 职责、明确不做的事、输入/输出标准、业务术语、遇到不确定事项找谁 |
| 学习材料 | 已授权公司文档/示例/知识资产 ID 和版本；不把整个历史聊天或个人记忆复制进去 |
| 可执行方法 | 配置内容/版本、指令不可变快照、skill 版本与适用条件引用；可取回字节及实际加载另验，不假定底座已提供完整历史 |
| 能力需求 | 所需浏览器/文件/工具/模型协议、数据范围和设备能力；声明需求不是授予权限 |
| 就绪检查 | 当前权限、版本兼容和实际加载、工具探测、一个小型岗位样例及验收证据 |
| 治理 | 公司/部门范围、维护人、发布者、版本、来源与退役状态 |

员工可用岗位包理解要求并配置有权使用的 AI；负责人维护获授权包。真人岗位材料沿选定内容服务/资产，Bot 指令优先 Multica 既有正文载体；缺不可变历史时由 B04 补保留版本和 GC 证据。组合保存引用与治理元数据，不再造第二可编辑指令库，也不把真人建成 Bot。

“已登记配置”“已安装”“已加载正确版本”“岗位检查通过”分别展示。adapter 返回 unsupported、缺少许可/工具、版本 hash 不符都不能显示已就绪。试验使用合成/获授权输入，不因入职自动对外发邮件或注册账号。

项目临时背景作为本次任务/run 的授权输入叠加，不为两个并行项目反复改写同一个公用 Agent 全局指令。岗位包更新生成新版本，既有实例选择是否迁移；安全撤权立即按运行授权协议处理，不能靠固定版本继续访问已撤销资料。

### 3.3 小队模板：可复用配方；小队实例：本次真实团队

模板最少包含用途/不适用场景、参数、真人/Bot 槽位、Bot 能力/岗位包版本、任务蓝图与交付依赖、验收角色、输入要求、费用和维护/发布责任。沿 Multica 的 Agent/Squad/任务关联复用；模板格式、真人槽位和企业范围不足时作最小扩展，不沿用 Paperclip TASK/PROJECT 包作为运行依赖。

实例化填写真实目标/输入，映射已有 user/Agent，选有权群/项目，预览新增/绑定/变更/缺项并重验权限，再建立 Multica 任务。小队实例只保存关联 ID、确定版本和准备状态；执行事实仍在 Multica，一个群不必等于一个项目，一次项目不必新建整队 Bot。

模板可由员工或负责人创建维护；提交部门/公司共享是独立发布权，不因拥有模板就自动向全公司发布。首版自然语言辅助生成/修改受约束表单和差异，不支持任意插件 YAML、可执行安装脚本或公共模板市场。

模板不携带：人员现成授权、设备池 grants、Key/Cookie、旧 run/session、私人目录、原 Bot 记忆、已完成任务状态。获准业务知识用资产引用；导入后逐项重新验权。模板升级不静默修改已组建小队；替换成员重新检查职责和资料权限，不要求原作者电脑在线。

**对话组队与 Leader 自行组织（2026-11-06 补核）：**Multica 已有 squad create/update、member add/remove/set-role 的 CLI/API，Leader 已有 roster、结构化派工、evaluation 与结果后再次协调，不需要重做团队系统。自然语言不应永远停在生成表单：已有明确委托内的组队/角色调整应落到原生写操作并给真实回执；超出委托才申请，不把每次派活变成审批。Ethan 已确认按这个受限自治方向收敛；具体接口/政策参数仍未冻结，真实合成实验的权限与最终汇总尚未通过。

必须区分：从已有成员选择执行者、修改小队成员、创建永久 Bot、授予资料/设备权、扩大费用是不同动作。现有 canManageSquad 按创建者/admin/owner 而非 leader_id；task token 用户绑定 runtime owner，不能直接代替发起员工的组队授权。优先复用原生 API，补本次委托、幂等结果和审计身份，不向 Bot 下发管理员 PAT；组队不自动增加资料和设备权限。具体证据、三项目取舍与失败样本见 [对话组队补核](MULTICA-BASE-EVALUATION.md#2026-11-06-对话组队leader-权限与企业能力补核)。

OMB 的组队变更计划/差异、条件校验、回执/Undo 可借鉴，Paperclip 的动作授权、超额/招聘政策门禁可借鉴；结果仍是唯一 Multica Squad/Issue。保留获权协调的自动后续，不沿用 OMB 的 Chief 审批级别自动提升，也不沿用 Multica 普通评论普遍唤醒队长作为公司默认。

#### Leader 自主组队的首轮边界

| 动作 | 默认处理；实际写入仍需当前授权 |
|---|---|
| 从可见、可调用且适配任务的现有 Bot 中选人，拆分/派工/催办/汇总 | 在本次委托和根协作限额内自主执行；有可靠回执，不为每一步追加人工批准 |
| 创建本次小队、修改其成员或职责 | 发起者/明确授予者须有对应权，绑定本次目标和对象；预览与应用条件一致。Leader 名称、Bot owner、设备 owner 不自动授予管理权 |
| 修改他人小队、换 Leader、新建永久 Bot、扩大资料/设备权或预算 | 没有独立明确授权就拒绝/交有权者处理；首轮不增加复杂招聘/通用审批 UI，不默许所有操作 |
| 成员回传后继续协调 | 只消费本轮登记依赖的真实结果/缺项；晚到结果要对账，普通讨论不唤醒；不能由一个成员冒充另一成员交付 |

同一动作真人直接调用与 Bot 受托调用必须遵循相同业务政策。设备管理人的资料承载资格只是运行前提，不是扩大委托；账号、Bot、设备三者留痕。对话建队不能只返回“创建成功”，还须可核对归属和请求人实际能否按委托管理；失败重试不得重复建队或篡改既有队伍。

实测登记见 [合成组队实验](MULTICA-BASE-EVALUATION.md#2026-11-06-合成组队实测权限-fail汇总未闭环)：A 直调 403、受托 Bot 修改成功和创建归 B 为 FAIL；成员回传局部成立，最终汇总截至采集未闭环。其他自治动作仍未测，不能以这次建队成功概括为自治管理已完成。验收按 MC-01G/05G，不新增第九个模块。

### 3.4 skill 升级：方法改进，不是模型训练或运行器自修改

1. **证据：**原 task/run、确定交付版本、纠错/成功依据、适用反例和来源权限；区分通用方法、项目事实与环境故障。
2. **候选：**从确定基础版本生成隔离候选，保留最小 diff、正文/资源 hash；不得试改生产 live 内容。Multica 现有 skill 载体优先复用，候选隔离是否具备须验证，不假称已有 managed fork。
3. **评估：**至少原案例与不同输入，预先质量/权限标准、独立输入身份和业务判断。评估运行复用 Multica task/run＋本地 DSH，不开第二测试执行器。执行 succeeded 不等于业务合格；模型自报不能替代有权评审。测试快照、输出、费用和判断按公司保留政策留证。
4. **发布：**再验来源/受众、发布权、当前基线和证据，通过条件写入生效；失败、过期候选不发布。具体条件事务与持久化能力待 B03/B04 验证，不以 current/latest/release 字段冒充审批。
5. **实际使用：**普通新 run 固定获准配置/指令/skill 组合；DSH 只读物化并核对正文、资源及实际消费路径。模板 hash、目录 digest、登记或同步成功不能证明已加载；缺失/unsupported/不匹配在模型调用前阻塞，不退 latest。
6. **观察/撤回：**新任务留验收、人工修订、失败和真实费用。问题版停止新使用；回退获准旧内容形成新的生效记录并复验。运行中不热换版，历史不改写，安全撤权不因固定版本而豁免。

最低闭环保留：成功复用、评估拒绝、过期候选冲突、撤权拒绝和回退后新任务验证。全公司私密对话扫描、自动全员发布、训练模型及改 harness/插件/平台源码均不在首版。

### 3.5 三道版本关口

- **新 run 选版：**明确解析已批准组合，校验当前政策及可取回内容。Multica 是否支持完整 pin 及内容历史待验证，不继承 Paperclip 的 enableBetaSkills 等实现条件。
- **已准入 run/接续：**留本次真正采用的配置、指令、skill、工具和输入版本；接续使用已确认检查点及效果对账，不从浮动 latest 重建历史。恢复不是进程或原始会话搬迁。
- **设备实际消费：**DSH 默认个人/项目搜索路径需关闭或受控，首版只挂本次只读版本投影；同名覆盖、缺文件/hash 不符阻塞。工具、slash、环境/plugin 注入都检查，mandatory skill 缺失不能降成普通文本。固定 DSH 源码反例仍有效，组合须实测。

### 3.6 版本记录：模板、实例、小队和 run 独立

| 对象 | 必须记录 | 不可假定/失败边界 |
|---|---|---|
| Bot 模板 | 来源、确定内容版本、职责/配置配方、维护/发布记录 | hash 不是历史内容；缺字节不能回退 |
| Bot 实例 | 稳定 ID、采用的模板版本、当前生效配置/指令/skill 组合 | 升级不换身份；动态资料/权限/设备不能由旧版复活 |
| 小队模板/实例 | 模板独立版本；实例成员映射与采用版本 | 模板升级不静默改实例，不克隆整队 Bot |
| 指令/skill | 唯一正文载体、不可变内容、资源 hash、保留根、候选/批准状态 | 优先复用 Multica；未验证历史/GC/pin 前不得宣称具备 |
| run | 实际组合、输入版本、设备 attempt、加载证据、结果/费用 | 每轮关联历史，不能只记 Bot 当前配置 |

有实质变化才追加版本，重试幂等；先持久化校验内容，再条件生效。初版没有配置 revision 时保存去秘密的有效快照/指纹并标明来源，不伪造 revision。任务工作区保存点不自动覆盖 Bot 公共文件；连续两次指令更改必须可取回，失败保存不得生效，GC 后保留字节和整组回退后的实际加载必须验证。不能为运行旧版反复修改共享 Bot 全局配置；不支持 per-run 组合则阻塞并评审适配。

**版本对象纠偏（2026-11-06）：**Multica 原生 plugin package 有不可变发布包、文件/digest、指定版本安装和升级确认，应优先评估复用；不能笼统称“Multica 没有版本历史”。但普通 skill 编辑更新当前行、claim 解析当前启用内容，是另一条路径；插件历史不能自动证明普通 skill/Bot 配置具备批准发布、历史字节保留、整组回退和 run 实际固定加载。B03/B04 按对象补差，不再造平行的正文编辑库，也不跳过 G2 版本验收。证据见 [Evose 对读 §7.4](EVOSE-PRODUCT-RESEARCH.md#74-新增源码证据索引)。

### 3.7 生效与恢复门禁

版本留痕、评估、批准组合、执行分开。模板预览与应用绑定同一内容及规范化效果清单，列明已有真人/Bot、能力、权限与暂停的例程；每步保留幂等回执，未知先对账。跨服务不天然原子：C03（DRAFT）须明确生效原子点、失败补偿和对账，新 run 准入核验整组，不以外围预检或 partial success 冒称已生效。

正式投影只读，任务自我改进只产候选；UI/API、自动回写和运行中写入一律过相同门禁，无法收口先关闭。测试输入/输出/模板、历史与缓存继承来源限制；脱敏后的扩大传播用独立安全 ACL 根，不扩大含私密历史的旧身份。回退是当前权限与基础版本下的新变更，不复活凭据、不改旧 run、不只回配置就宣称整 Bot 回退。

这些是 B03 模板发布、B04 资产版本与 C03/C04 的待验要求，不是 Multica 已有能力证明。旧 Paperclip 版本/pin/GC/test 到期反例保留于迁移前归档及参考研究，只提供可证伪设计，不再作为当前 API/存储依赖。

## 4. 用一条真实业务走完，而不是只列功能

**建议首个通用样例：跨部门活动方案。**两个部门、两名真人分别负责运营与内容；两名专业 AI 负责资料分析与方案草拟；组织助手是可选协调角色，逻辑角色数量不是并发容量指标。

1. 运营员工提出“为下次新品活动准备方案”，补齐时间、受众、预算约束和验收内容。负责人也可从部门目标发起同样流程；员工发起不自动承诺另一部门资源。
2. 组织助手推荐已有分析/草拟 AI，套用一个小队模板；运营、内容真人映射到槽位，明确一名业务负责人和验收人。资料分析、内容草拟两个岗位包完成资料/工具/版本检查；缺跨部门权限交给有权者处理。
3. 建立资料核对、活动草案、复核交付任务。内容员工认领资料整理；分析 AI 获授权资料后产出分析，草拟 AI 接收该已确认版本再草拟；其他无依赖工作可同时运行。认领结果只能有一个赢家。
4. 员工助手在本人设备、公用 AI 在授权设备池本地执行；自动保存文件。分析阶段交接有资产版本和接收回执。负责人从部门视图跟进，跨部门参与者只见获授权项目流转。发现来源或数字错误，退回对应任务修订，不靠在群里说“已完成”。
5. 公司确认归档后提交验收，指定人验收方案。复盘发现“方案未标注数字来源”，生成检查来源的 skill 候选，另形成岗位包/模板变更建议，分别评估和发布，不把本次客户数据变通用模板。
6. 下次另一员工用同一已发布模板，换新活动输入；新任务实际加载已批准 skill 版本，检查来源缺失是否被发现。原维护人退出后新维护人仍可使用公司版本；未上传文件或个人连接依赖明确阻塞，不能宣称全部资产已接管。

同一套产品再接千川只读分析；关闭千川连接器后通用场景仍成立。首版不发布广告、不修改预算、不发送真实营销邮件。

**完整人机操作走查：**上述业务中补追问/真人回答、具体许可/拒绝、执行中补充与改撤、按范围停止/明确继续、文件确定版本提交和指定人验收；随后才做平台任务/资产纠错及 skill 迭代；外部知识条件写按 KD 后接。员工/负责人同一界面、按当前权操作。展示权威见 [体验 §3.5–4.2](PRODUCT-EXPERIENCE.md)，控制语义见 [群协作 §4.6](DISTRIBUTED-COLLABORATION.md)，知识条件更新/恢复见 [资产 §2.6–2.7](ASSETS-AND-LEARNING.md)，不在本流程另定义一套状态。

## 6. 首版范围与建设顺序

- **P1：**六步中的前四步最小纵向切片；可选组织助手与人工入口；两份预置最小岗位包、一个预置小队模板的受控实例化（仅样例，完整维护/发布体验在 P2）；明确责任/验收和局部失败；统一追问/许可/补充/停止、文件交付与平台任务/资产纠错进入首条切片；外部知识条件写不在此切片，可提交复盘候选。只预置最小样例，不做模板市场/通用编辑器。
- **P2：**完成六步闭环：员工/负责人均可在授权内自然语言辅助修改岗位包/小队模板；沿同一任务/run 评估，对候选评审发布、再次复用、回滚和维护人交接。模板/skill 发布与数据/设备使用权分开。
- **P3：**千川只读与非千川双场景，换员工/输入再跑；故障、安全、成本、备份与 LC 门禁齐备后内部发布。
- **后续：**更多模板、批量评估/健康检查、跨公司市场、复杂连接器、语音及工作流按证据另立项。最小案例评估不得推到后续。

首版最小素材建议为“资料分析”“内容草拟/复核”两个岗位包和一个“跨部门活动方案”小队模板，具体业务材料、维护人、发布者、角色兼任、预算与提醒时限在试点前由业务责任人填定。不是等待这些姓名才能讨论架构，也不把建议值冒充已确认政策。
