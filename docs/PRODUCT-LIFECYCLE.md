# 从目标到团队、交付和持续复用

> 2026-11-05，产品流程与 MVP 设计评审稿。Ethan 已确认“提出目标→组建人和 AI 团队→拆分认领任务→协作交付→复盘沉淀→下次复用”的方向，员工和负责人都能使用。以下具体字段、默认策略和验收条件为本轮建议，不表示实现或实验已通过。本轮只修订 docs。

## 1. 产品主线与不变边界

morchat 是公司的人机协作平台，而非 Bot 集合、单人助手或千川工具。公司保留工作成果、方法和可维护的能力，但不保留个人隐私，也不因留存而向全员开放。

同一个客户端提供工作群、我的工作、部门/公司/获授权项目面板、AI 同事和资产目录。员工可发起工作、建群、维护获授权的岗位包/小队模板；负责人使用相同入口，多出实际被授予的目标管理、部门分派和发布权限。老板不是唯一能看面板或下目标的人。

中央仍是协作控制与核心数据服务；模型推理在公司管理的云端，完整 harness 和工具在获授权员工设备。组织助手、入职测验、复盘和 skill 测试的模型调用也必须有真实 Paperclip task/run，走同一本地派发、授权、自动保存和计量链。没有合格设备时显示 AI 工作等待；不中央代跑，也不阻止人工建群、认领或验收。

工作流画布、通用流程引擎、Coze/n8n 集成继续暂缓。小队模板是角色和交付的组合配方，不是一套新的低代码系统。语音、自动注册外部账号、发送邮件和生产业务写入不因参考资讯而进入首版。

### 1.1 统一定位：Bot 就是 AI 同事

产品层统一称 **Bot（AI 同事）**；工程和上游 API 中继续称 Agent。一个正式 Bot 实例对应同一个 Paperclip Agent 身份，不另建一套 bot 身份/可写配置，也不把真人映射为 Agent。员工助手、部门公用 Bot、组织助手 Bot 是不同职责/使用范围，不是不同运行引擎。

Bot 有稳定身份、职责、维护人、授权范围和能力版本；不是模型、harness、电脑、进程或某一次聊天。一个 Bot 可参与多个获授权小队，执行多项隔离任务；同名不等于同一身份，换设备/升级能力不应新建影子 Bot。模型/工具/电脑权限仍分开管理。

任务内部临时子 Agent 是执行单元，不自动成为名册中的公司 Bot。确需长期复用或独立治理时，再经过已有 Agent 创建/授权流程形成正式 Bot；不能把每次拆分都当扩编。

### 1.2 模板、实例、工作和运行的关系

| 对象 | 定义与关系 | 版本/身份边界 |
|---|---|---|
| Bot 模板 | 创建或更新一类 AI 同事的配方：角色、默认配置、岗位入职包/指令内容、skill 引用、工具需求 | 优先原生 AGENTS 包或经审查的参考包；记录来源、内容 hash 和可用的包版本；没有成员、设备、凭据、旧记忆或现成权限 |
| Bot 实例 | 公司名册中的一位具体 AI 同事，映射唯一 Paperclip Agent；可由模板创建，也可复用已有实例 | 身份稳定；保存来源模板及已生效能力版本引用，升级不换身份；实际授权另外授予 |
| 岗位入职包 | 职责、材料、质量要求与就绪检查；可供真人学习，也可被 Bot 模板/实例引用 | 不是另一种 Bot，也不强制每个 Bot 配一份独立副本；正文/材料复用已有载体 |
| 小队模板 | 角色槽位、Bot 模板/能力要求、真人岗位、任务蓝图和交接/验收规则 | 复用 TEAM 包/模板能力，补真人与企业范围；不是工作流引擎，也不是一组已获授权成员 |
| 小队实例 | 本次合作的实际真人和 Bot、目标/群/项目关联及确定的模板/能力版本 | 优先绑定已有 Bot，不为每次组队克隆整队；升级模板不改写已组建小队 |
| 任务 | 一项有输入、产出、承接者和验收要求的工作，唯一事实在 Paperclip issue | 任务身份不随设备或执行重试变化；换承接者有明确授权/交接 |
| 任务运行 | Bot 执行任务的一次 run；派发/恢复另关联设备 attempt、租约和工作区 | 一个任务可先后有多个 run/attempt；一个 Bot 可并行多个隔离 run；运行固定实际使用的能力和输入版本，不等于新 Bot |

关系主线：**Bot 模板 → 创建/受控更新 Bot 实例；小队模板 → 绑定真人和已有 Bot → 小队实例；任务 → Bot 的 run → 具体设备 attempt。**模板是配方、实例是身份/成员组合、run 是工作过程，三者不能互相替代。技能是 Bot 可复用的方法，不是它的身份或私人记忆。

例如“运营分析 Bot”今天做活动分析、明天做千川只读分析，仍是同一位 AI 同事的不同任务；同一模板可创建不同部门的独立 Bot，但不因来源相同共享权限/会话。

## 2. 六步流程：每一步有真实产物和责任

| 步骤 | 员工/负责人怎么用 | 系统形成什么 | 进入下一步的条件 |
|---|---|---|---|
| ① 提出目标 | 从工作群、我的工作或目标面板填写，或请组织助手用自然语言整理 | 目标简报：预期结果、输入与来源范围、验收标准、期限、业务负责人/验收人、资源/费用约束；关联原生 goal/project/issue | 缺项清单有补充人；未确认范围只作草案，不代表其他部门已承诺投入 |
| ② 组建人和 AI 团队 | 推荐已有同事/AI，选择岗位包或小队模板，查看差异后按权限应用 | 小队实例、角色槽位与真实成员映射、工作群/项目关联、待邀请/待授权/缺能力清单；必要时提出新增 AI | 人员接受或有权分派成立；工具、资料、版本、设备分别通过检查；未就绪角色不能显示可执行 |
| ③ 拆分认领任务 | 查看拆分建议，调整交付物/依赖，自己认领或按权委派 | Paperclip 真实任务与依赖；唯一当前承接者、业务责任、验收人、输入版本、产出要求和期限 | 认领在服务器原子决定；输入授权和真实依赖满足；不能因看得到任务就抢走别人的工作 |
| ④ 协作交付 | 群内跟进、补充资料、交接阶段成果、退回修改或验收 | 任务/run、自动保存点、版本化成果、交接回执、验收记录和实际费用 | 文件获公司持久确认才可提交验收；指定验收人接受才算验收完成；派单/发消息/AI 自检均不算完成 |
| ⑤ 复盘沉淀 | 在已授权任务上点“复盘/改进方法”，指出成功经验或错误 | 知识、岗位包、小队模板或 skill 的改进候选；关联来源证据、基础版本、差异、适用/不适用条件、评估案例 | 先分清项目事实与通用方法；候选经评估及对应发布权检查，不因“做对一次”自动成为公司规则 |
| ⑥ 下次复用 | 在新工作中选择已发布模板/能力，换实际成员和输入 | 新实例、新 task/run；固定模板/岗位包/skill 版本；重新授权后的输入清单；实际加载证据 | 不继承旧会话、旧凭据和旧授权；能力缺失/版本不符显示阻塞，不能偷偷改用 latest；新结果再次回到复盘 |

这里的“草案、准备中、可用”和交接回执只描述方案/组队操作自身，不是另建一份可写任务状态机。任务、执行、保存、验收四类状态按 [工作接续协议](D:/dev/morchat.co/docs/WORKSPACE-CONTINUITY.md) 显示；公司目标的经营结果另有指标，不以任务完成率冒充。

### 2.1 最少责任关系

- **发起人**提出需求；**业务负责人**管理范围、优先级和阻塞；**执行者**承接具体任务，可以是真人或 AI；**验收人**判断是否满足约定。小任务允许同一真人兼任业务负责人/验收人，但必须显式显示，不默认所有任务加第二审批人。
- 每项任务一个当前主承接者，协作者用关联成员/子任务表达，不用两个可写负责人字段争夺权威。AI 承接不消除人类业务责任。
- 真人使用真实 user，AI 使用 Agent。原生 responsibleUserId 是服务端责任身份链，不直接当任意 RACI 编辑栏；业务负责人/验收人等扩展不覆盖其安全语义。
- 同部门普通任务可读不等于可认领已承接工作、转派、发布、读私密群或使用同事电脑。跨部门邀请/请求协作不等于获得对方部门的派单权。

### 2.2 变化、重试与交接不是异常边角

- 目标/验收标准变化先给出差异和受影响任务，由有权者处理已认领工作的重排；不静默覆盖在途交付约定。
- 组队是一组可恢复操作：每次操作及各步骤有幂等标识、原生对象 ID 和回执。群创建成功、任务失败时显示部分成功，重试只补缺项；不重复造 AI/群/任务，不自动删除已经被他人使用的对象。需要原生幂等或可查询确定结果；结果未知先核对，不盲重放。
- 业务交接包含 task ID、接收方、授权输入/产物版本、待办与验收口径，区分已送达、已承接、缺权限/资料。群邀请不公开来源群全部历史；依赖完成也不自动授予输入读取权。
- 同一个任务已通过派单唤醒，就不再因同一条 @ 重复启动；AI 回报不触发无限互聊。跨设备无冲突任务并行，只有依赖、资源冲突、预算或无合格设备才等待。

## 3. 四类能力如何落地

### 3.1 AI 组织助手：可选的组织能力，不是超级管理员

**入口：**“帮我把目标组织起来”“用这个模板组队”“检查小队缺什么”“复盘这次工作”。员工和负责人共用入口，结果受各自授权约束；也可不经助手直接操作表单、群和任务卡。

**首版行为：**澄清少量缺项 → 检索可见且可使用的现有同事/AI/模板 → 提议角色、任务、交接和费用归属 → 展示新增/复用/变更清单 → 依据委托权限执行可执行项，缺权项交给相应授权者 → 显示真实回执/缺项。优先复用，不以新增 Bot 数量为成绩。

该能力体现为组织助手 Bot，由 Paperclip Agent/指令和受控工具承载；可参考其 create-agent/Reflection Coach 方法，不另起一套组织规划后台。首版可配置一个组织助手逻辑角色，但每次工作独立 task/run/context，可并行，不能变成全公司唯一串行进程。工作人员可以暂停它，手动流程仍可继续。

“自然语言创建”不授予任命员工、扩大部门权限、读取所有历史、无限创建 AI、开启定时任务或改公司安全策略的权力。有明确授权的动作不必逐步人工二次确认；增加权限/预算或超出委托时才走相应门禁。首版模板例行任务默认不激活，创建逻辑 AI 不代表已有设备可运行。

所有 Agent 创建/模板安装/原生 UI 写入口必须执行相同公司政策。未验证 Team Catalog 导入与 agent-hires 一致前，不向员工/助手开放原始导入写入口；预览和受控应用不等于长期把每次组队变成管理层审批。

### 3.2 岗位入职包：职责、材料和“确实能工作”的检查

| 内容 | 最小要求 |
|---|---|
| 角色约定 | 职责、明确不做的事、输入/输出标准、业务术语、遇到不确定事项找谁 |
| 学习材料 | 已授权公司文档/示例/知识资产 ID 和版本；不把整个历史聊天或个人记忆复制进去 |
| 可执行方法 | Paperclip 配置 revision、指令内容的不可变快照/hash、skillId/versionId 与适用条件引用；不将历史指令接口当新保存的版本保证 |
| 能力需求 | 所需浏览器/文件/工具/模型协议、数据范围和设备能力；声明需求不是授予权限 |
| 就绪检查 | 当前权限、版本兼容和实际加载、工具探测、一个小型岗位样例及验收证据 |
| 治理 | 公司/部门范围、维护人、发布者、版本、来源与退役状态 |

员工可用它了解工作要求并配置有权使用的 AI；负责人可维护本部门获授权的包。真人岗位材料走公司文档/资产；Bot 指令当前正文优先复用 Paperclip managed instructions/AGENTS.md 包；其新文件保存不追加完整历史，优先复用 durable blob/manifest 并补历史保留根，或接公司既有保留资产。morchat 保存组合、快照引用和权限元数据，不再造第二可编辑指令库，也不将真人建成假 Agent。

“已登记配置”“已安装”“已加载正确版本”“岗位检查通过”分别展示。adapter 返回 unsupported、缺少许可/工具、版本 hash 不符都不能显示已就绪。试验使用合成/获授权输入，不因入职自动对外发邮件或注册账号。

项目临时背景作为本次任务/run 的授权输入叠加，不为两个并行项目反复改写同一个公用 Agent 全局指令。岗位包更新生成新版本，既有实例选择是否迁移；安全撤权立即按运行授权协议处理，不能靠固定版本继续访问已撤销资料。

### 3.3 小队模板：可复用配方；小队实例：本次真实团队

模板最少包含：用途/不适用场景、参数、真人/Bot 角色槽位、Bot 模板或能力要求、岗位包版本、任务蓝图和交付依赖、验收角色、输入要求、费用归属规则、维护/发布责任。任务蓝图优先引用 Paperclip 包中的 TASK/PROJECT 定义；缺少真人槽位的部分用 composition 扩展映射，不建第二个通用任务定义平台。

实例化时填写真实目标和输入，映射现有 user/Agent，选定有权使用的工作群/项目，预览新增对象和缺项，重新检查授权，再创建真实任务。小队实例只保存关联 ID、确定的版本、成员映射及准备状态；执行事实仍读 Paperclip。一个群不强制等于一个项目，一次项目也不必新建整队 AI。

模板可由员工或负责人创建维护；提交部门/公司共享是独立发布权，不因拥有模板就自动向全公司发布。首版自然语言辅助生成/修改受约束表单和差异，不支持任意插件 YAML、可执行安装脚本或公共模板市场。

模板不携带：人员现成授权、设备池 grants、Key/Cookie、旧 run/session、私人目录、原 Bot 记忆、已完成任务状态。获准业务知识用资产引用；导入后逐项重新验权。模板升级不静默修改已组建小队；替换成员重新检查职责和资料权限，不要求原作者电脑在线。

### 3.4 skill 升级：改进工作方法，不是模型训练或运行器自修改

1. **捕获证据：**原 task/run、交付版本、员工纠错/成功依据、适用与反例、来源权限。先判断是通用方法、项目事实还是环境故障；不是所有内容都变 skill。
2. **形成候选：**优先用 Paperclip managed fork 隔离候选，保留基线 skill/version、最小 diff 和正文/资源 hash。原生编辑会推进 currentVersion，未经验证不得在生产 live skill 上直接试改。
3. **评估：**复用原生 test-inputs、test-run-templates、test-runs 和真实 skill_test issue；至少原案例与一个不同输入回归，各用独立 inputId。对照预先约定的质量、权限和适用条件；测试任务 succeeded 只是执行完成，不等于业务评审通过。评价由有权评审者记录，可用 AI 辅助，不由生成者一句“通过”替代。
4. **发布：**复查来源与目标受众权限、当前基线及证据；有权发布者更新已发布版本组合/Agent 绑定。不自建正文或评测运行库；morchat 保存评判、发布记录和原生 testRunId。回归失败或过期候选不能发布。
5. **新任务实际使用：**解析明确获准版本，Paperclip run 保存选用快照；本地 DSH 只挂本次只读投影，核对实际正文与引用资源 hash，覆盖 skill 工具与 slash 注入两条路径。目录列表 digest、配置登记和同步成功都不能单独证明实际加载。
6. **观察/撤回：**新任务关联人工修改、验收和真实费用。问题版停止新使用；通过受支持的明确旧版本绑定，或原生恢复旧内容追加新版本后验证发布。运行中任务不静默热换；旧记录保留真实版本。安全撤权需要暂停/终止与重新授权，不能为“复现”继续泄露。

最低闭环必须有成功复用、评估拒绝、过期候选冲突、撤权拒绝和回滚后新任务验证。自动批量扫描私密对话、全自动全员发布、修改 harness/插件/平台源码及训练模型均不在首版。“持续升级”指有证据的组织能力迭代，不承诺无人监管的递归自我升级。

### 3.5 三道版本关口，不用界面状态替代证据

- **普通新 run 选版本：**固定 Paperclip 样本的 Agent 历史版本 pin 受 enableBetaSkills 控制；关闭时新配置 pin 被拒，已存 pin 在普通新 run 选择时可能转 current。P0 必须验证可支持的显式 pin 路径，必要时评审开启该功能；不支持则阻塞发布复用，不能静默 latest。
- **已准入 run 恢复：**原生 contextSnapshot.skillVersions 保存实际选择，恢复沿用；Studio skill test 固定其保存版本，独立于 Beta 开关。不能误写成“Paperclip 没有运行版本快照”。
- **本地实际物化/消费：**skills/sync 可能先保存配置再返回 unsupported。DSH filesystem provider 默认搜索个人/项目 roots，首版显式 includeDefaultRoots:false，仅挂只读投影。其目录 hash 不是正文 hash；文件缺失、同名覆盖、hash 不匹配均阻塞。复用 provider/工具与扩展点，不重写 agent loop。

### 3.6 版本记录：复用已有历史，补内容缺口和关联

| 版本对象 | 已有能力与限制 | 首版处理 |
|---|---|---|
| Bot 配置 | Paperclip agent_config_revisions 有修改者/时间、前后配置、changedKeys、回滚来源；支持查询与回滚 | 直接复用覆盖字段的历史；不是所有权限、指令文件和整个运行目录的统一快照 |
| Bot 指令/附属文件 | 已有 durable S3 blob/hash/current manifest；新保存不追加完整指令历史，GC 只保当前根，旧 history/restore 不能保证新历史 | 保留 Paperclip 编辑权威，复用持久化并补历史保留根或既有保留资产；获保留旧版字节须在 GC 后仍可取，不要求手动 commit |
| Skill | 原生不可变内容版本、测试与恢复已有 | 复用原生 skillId/versionId，不重做正文、版本表或评测执行引擎；发布/使用权限仍另验 |
| Bot/小队模板 | 包格式、预览、来源和 contentHash 已有；部分包有 packageVersion | 复用包及来源版本；hash 只能识别内容，缺少历史包时用既定 Git/版本资产归档，不能只留浮动链接却声称可回退 |
| Bot 能力版本清单 | 配置、指令、skill 各自有不同载体，尚不能当成一个原生“完整 Bot 版本” | morchat 只关联上述不可变引用、来源模板、变更原因/操作者/时间、评估和生效记录，不新造版本存储引擎 |
| 本次 run 版本证据 | 原生有 skill 选择快照和运行记录；本地实际消费仍须验证 | 关联能力清单、实际配置内容指纹、指令/资源 hash、skill 版本和输入资产，缺失不以 latest 代替；设备与当前授权另存，不由版本恢复 |

**明确修正此前结论：**“存在 agent_instruction_revisions 表或 history/restore 路由”不意味着每次新指令保存都写入历史；固定样本的 commit 路径写当前文件与活动记录，并非追加旧指令正文版本。Bot 配置 revision 也不包含指令文件字节。[实际提交路径](https://github.com/paperclipai/paperclip/blob/40ea7a9b8994e9bdb3d13794b5847388be0f7a92/server/src/services/agent-instruction-revisions.ts#L215-L350)、[配置字段](https://github.com/paperclipai/paperclip/blob/40ea7a9b8994e9bdb3d13794b5847388be0f7a92/server/src/lib/agent-records.ts#L22-L38)、[官方说明](https://docs.paperclip.ing/reference/api/agents/#instructions-bundle)。

能力清单是“这次生效由哪些现有版本组成”的元数据，不是第二份可编辑 Bot。Bot 模板描述可创建的配方，Bot 实例的能力清单描述该具体 Bot 已选择的组合，两者不能用一个版本号含糊替代。清单不包含原始 Key、私人记忆、动态项目资料或可复活的旧授权。首次创建若没有可引用的原生配置 revision，应保存去秘密后的有效配置快照/指纹并标明来源，不伪造原生 revision ID；后续仍优先引用原生记录。

**每次迭代的生效规则：**

1. 有实质变化才追加版本/记录；相同内容重试保持幂等。候选、修改者/来源任务、基础版本及失败结果可追溯；身份 ID 不因迭代改变。
2. Bot 模板/小队模板或 skill 升级只产生新候选/发布版本，不静默更新所有既有 Bot 和小队。选择采用后生成新的能力组合；新 run 使用已批准组合，旧 run 保留实际历史，安全撤权仍立即按既定协议执行。
3. 指令/模板补快照是系统动作，先持久保存所需旧/新内容并校验，再让新组合生效；未归档、基线冲突或配置与快照不一致则阻塞生效/新 run。任务工作区保存点不自动等于 Bot 公共指令历史，须显式纳入并验证。
4. 首版 Bot 自我改进默认产出候选，不直接覆盖正式能力。原生 UI/API、任务中自改文件与自动回写路径都要进入相同版本/授权门禁；无法拦截或对账的写入口先不开放。不能只有我们的按钮留版本，其他路径却静默覆盖。
5. 回退复用配置原生条件事务、Skill 原生恢复及获保留的指令/模板内容，经基线/权限检查形成新的生效记录；现有配置 rollback 路径不自动保证 expected revision，需要接原生 CAS。回退方法不复活已撤销权限/凭据，不热换在途任务；不能只回配置却声称整个 Bot 已回到旧版。

上述补齐优先复用原生 durable blob/manifest、GC 保留扩展或既有版本资产，以及 Paperclip 记录与访问策略，不引入第二身份、任务或版本引擎。P0 需证明：新保存不能靠旧 history 路由恢复的情况被识别；连续两次指令变更可追溯字节、一次失败保存不生效、整组回退后的新 run 实际加载正确内容。还需验证 per-run 能否物化选定配置/指令/skill 组合；不能为模拟旧版本反复修改共享 Bot 全局配置。做不到则阻塞受影响的版本运行并评审适配，不偷偷用最新或创建影子 Bot。源代码阅读不是组合验收通过。

### 3.7 版本闭环的原生实施边界

版本留痕、候选评估、批准组合和实际执行是四件事。原生 durable 已有 current manifest/blob，仍需历史保留根/GC 证明；模板 preview/install 二次 prepare 不自动冻结，必须固定内部包及规范化效果计划，显式绑定现有真人/Bot、remote adapter、include 范围和暂停的 routine/trigger，按步骤留幂等回执，未满足依赖显示 BLOCKED。

生效采用基础 revision/发布组合的条件检查；回退走原生 CAS 和可取回内容，不把普通配置 rollback 当完整并发保护。跨服务不是天然原子事务：准备/持久化与生效分开，启用新 run 的权威关口核验整个获准组合及当前政策；任一步未知阻塞，不把 partial success 显示为“已生效”。C03 冻结时必须明确实际原子点/对账路径，不能只靠外围预检。

首版运行不直接改正式能力：原生 instruction tool、working-copy warm/stop apply 都要收口，正式投影只读，自我改进留为任务产物/候选；保留候选证据，不因拒绝 apply 丢失。最终技能集包括 task mention 与 environment/plugin 注入，须在全部解析后核验用途/版本；不能只检查 Agent 配置页面。DSH 缺失 slash skill 可降为普通文本，因此 mandatory skill 缺失须在模型调用前失败，不能把原生 fallback 当满足版本要求。

测试快照/输入/输出/模板、历史和缓存都继承来源权限；测试成功不等于可公开。脱敏扩大传播不能扩大旧私密 identity 的 ACL。细节与可证伪顺序见 [F01–F08、G2/G3](D:/dev/morchat.co/docs/DISCOVERY-BASELINE.md)。这些是必须适配/扩展的执行边界，不是已实现能力。

## 4. 用一条真实业务走完，而不是只列功能

**建议首个通用样例：跨部门活动方案。**两个部门、两名真人分别负责运营与内容；两名专业 AI 负责资料分析与方案草拟；组织助手是可选协调角色，逻辑角色数量不是并发容量指标。

1. 运营员工提出“为下次新品活动准备方案”，补齐时间、受众、预算约束和验收内容。负责人也可从部门目标发起同样流程；员工发起不自动承诺另一部门资源。
2. 组织助手推荐已有分析/草拟 AI，套用一个小队模板；运营、内容真人映射到槽位，明确一名业务负责人和验收人。资料分析、内容草拟两个岗位包完成资料/工具/版本检查；缺跨部门权限交给有权者处理。
3. 建立资料核对、活动草案、复核交付任务。内容员工认领资料整理；分析 AI 获授权资料后产出分析，草拟 AI 接收该已确认版本再草拟；其他无依赖工作可同时运行。认领结果只能有一个赢家。
4. 员工助手在本人设备、公用 AI 在授权设备池本地执行；自动保存文件。分析阶段交接有资产版本和接收回执。负责人从部门视图跟进，跨部门参与者只见获授权项目流转。发现来源或数字错误，退回对应任务修订，不靠在群里说“已完成”。
5. 公司确认归档后提交验收，指定人验收方案。复盘发现“方案未标注数字来源”，生成检查来源的 skill 候选，另形成岗位包/模板变更建议，分别评估和发布，不把本次客户数据变通用模板。
6. 下次另一员工用同一已发布模板，换新活动输入；新任务实际加载已批准 skill 版本，检查来源缺失是否被发现。原维护人退出后新维护人仍可使用公司版本；未上传文件或个人连接依赖明确阻塞，不能宣称全部资产已接管。

同一套产品再接千川只读分析；关闭千川连接器后通用场景仍成立。首版不发布广告、不修改预算、不发送真实营销邮件。

**完整人机操作走查：**上述业务中补追问/真人回答、具体许可/拒绝、执行中补充与改撤、按范围停止/明确继续、文件确定版本提交和指定人验收；随后才做知识纠正及 skill 迭代。员工/负责人同一界面、按当前权操作。展示权威见 [体验 §3.5–4.2](D:/dev/morchat.co/docs/PRODUCT-EXPERIENCE.md)，控制语义见 [群协作 §4.6](D:/dev/morchat.co/docs/DISTRIBUTED-COLLABORATION.md)，知识条件更新/恢复见 [资产 §2.6–2.7](D:/dev/morchat.co/docs/ASSETS-AND-LEARNING.md)，不在本流程另定义一套状态。

## 6. 首版范围与建设顺序

- **P0：**保留 Windows 原生隔离、公司 Key、并行、自动保存和跨机接续门禁；补组队入口一致性、人类原子认领、候选隔离、普通运行显式版本选择、真实加载和测试证据留存契约。只在获得后续实施授权后执行，不因产品流程写全就宣布可行。
- **P1：**六步中的前四步最小纵向切片；可选组织助手与人工入口；两份最小岗位包、一个小队模板的受控实例化；明确责任/验收和局部失败；原生追问/许可/补充/停止、文件交付与最小知识纠正进入首条切片，可提交复盘候选。只预置最小样例，不做模板市场/通用编辑器。
- **P2：**完成六步闭环：员工/负责人均可在授权内自然语言辅助修改岗位包/小队模板；复用原生测试，对候选评审发布、再次复用、回滚和维护人交接。模板/skill 发布与数据/设备使用权分开。
- **P3：**千川只读与非千川双场景，换员工/输入再跑；故障、安全、成本、备份与 LC 门禁齐备后内部发布。
- **后续：**更多模板、批量评估/健康检查、跨公司市场、复杂连接器、语音及工作流按证据另立项。最小案例评估不得推到后续。

首版最小素材建议为“资料分析”“内容草拟/复核”两个岗位包和一个“跨部门活动方案”小队模板，具体业务材料、维护人、发布者、角色兼任、预算与提醒时限在试点前由业务责任人填定。不是等待这些姓名才能讨论架构，也不把建议值冒充已确认政策。
