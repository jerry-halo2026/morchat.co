# Evose 产品结构与企业协作研究

> 2026-11-06，已登录页面只读走查与官方文档核查。研究输入，不是新的实现权威、契约冻结或产品验收。Multica 唯一底座不变；首轮多人、多 Bot 范围不变。本文不批准代码移植、外部产品部署或付费执行。

## 1. 结论

**Evose 值得作为整体产品结构参考，不应只被归为知识库或聊天框参考。** 它把日常使用、项目协作、能力维护和企业治理连接起来；项目内文件、任务视图、对话、成员、知识与能力、收件箱和审计保持同一工作上下文。这与我们的企业人机协作定位高度相关。

Ethan 本轮再次明确：看板、流程、排期和项目知识能力都是我们需要考虑的工作面。不能因为它们不是同一个技术概念，就把其中一部分排除；也不能因为入口名称相近就把未观察到的功能算成已实现。

- 看板回答任务处于什么状态；流程回答工作经过哪些业务环节；排期/甘特回答起止日期、前后依赖和延期。它们应成为同一项目、同一批任务的互补视图。
- 本次实际看到看板和业务流程视图，未看到带时间轴的甘特。Evose 另有“计划”，实际为定时触发 Agent/工作流，不是这里的项目排期。
- 项目“知识和能力”不是边角设置：规则、能力、知识库、记忆应说明人和 Bot 根据什么协作、可调用什么、引用什么资料、如何保留经验。
- 对我们最有价值的是上述对象关系与完整操作链；不是复制所有菜单，也不是引入另一个任务、调度或权限后台。

## 2. 证据与覆盖范围

主 agent 在已登录 IAB 采集实际页面、菜单和未提交表单；三个只读 subagent 分别核查项目/计划/通知、资料/能力、企业治理官方说明并对照现行契约。子会话无法访问主会话 IAB，因此没有把它们写成各自独立的浏览器实测。

证据标记：**UI** 为当前账号可见页面；**DOC** 为官方说明；**提案** 为针对 morchat 的设计判断；**未测** 包括真实执行、服务端权限和故障行为。UI 可编辑规则文案不是代码或强制执行证据。未取得 Evose 后台源码、固定部署 SHA 或源码许可证据，不存在已批准的源码直接复用清单。

没有发送模型请求、提交创建/编辑表单、邀请成员、变更权限、导入资料、触发计划、付款或读取凭据明文。走查切换过任务视图，结束恢复为原列表视图。页面状态可能被其他操作者更新：项目规则首次为 0，Ethan 指向该页面后复查为 6；这不是本次研究创建的内容。

覆盖当前可访问的六个一级入口，以及工作空间、组织管理的主要二级入口。**不等于所有资源详情和角色均已测试**：当前只有一个项目样本、一张表，项目成员为一名真人和一位 Lead Agent；多个列表为空。组织完整观测被套餐限制阻挡，未绕过；桌面策略、资源发布和多人真实执行未测。

以下登录态 URL 使用 `PROJECT_ID`、`WORKSPACE_ID`、`TABLE_ID` 表示已访问对象的脱敏标识；它们不是新增可调用路由或可直接访问的样本链接。统一域名为 [app.evose.ai](https://app.evose.ai/)。

### 2.2 项目知识和能力

Ethan 指定的 [项目知识和能力页面](https://app.evose.ai/project/244327586270834688/context) 已再次检查。它应成为我们完整项目工作面的重点参考。

| 分区 | UI 实见 | morchat 对应关系 |
|---|---|---|
| 规则 | 规则列表、创建/模板导入入口；复查有六组治理规则 | 项目工作约定与授权边界的可读入口；由版本/权限契约约束生效 |
| 能力 | 项目内工具和子能力集合、添加入口 | 项目需要的 Bot/skill/工具引用；绑定不等于授予全部成员工具权限 |
| 知识库 | 可从空间选择多个库挂载；当前 0/10，设置与添加入口 | 显式资料范围，不向所有 Bot 自动注入整个公司库 |
| 记忆 | 共享项目记忆开关、条目维护、批量管理；当前关闭、0 条 | 与资料原件、技能版本分开；关闭加载不等于撤权清理完成 |

六组规则文案进一步呈现一套可参考的协作模型：

1. 真人 Owner 与 Lead Agent 分工：人承担决策责任，Lead 负责协调。
2. 文件区分草稿、评审与正式成果，并描述关键文件版本引用。
3. 任务区分待规划、待办、执行、待评审、完成或取消；需要人决策时进入收件箱。
4. 成员分派说明 Lead 协调、能力标签匹配、子任务挂父任务以及不得自行提升角色。
5. 同一业务阶段可有多个子任务并行，跨阶段依赖须显式表达，阶段配置改变需要确认。
6. 边界分为直接禁止与需人批准，决策经验可回沉规则，违规进入审计。

**这些是可编辑项目规则表达的意图，尚未实测相应机制。** 其中字段名、阶段编号和命名规范不作为 Multica schema；规则文字也不能替代服务端 ACL、幂等、版本固定或 Windows 隔离。但它清楚说明我们不应只借菜单：应借“工作约定→人机执行→待人决策→结果回沉”的产品关系。

## 3. 官方说明与当前页面的差异

官方把产品分为使用工作台、构建空间和组织治理，并允许同一人跨层承担职责。值得借这种职责分层，但我们不能据此禁止普通员工维护获授权的 Bot/小队/技能。[三层架构](https://evose.ai/docs/en-US/use/why-evose/three-layer-architecture/)

官方 Schedule 说明计划可重叠执行、保留运行记录与完成通知；重试策略配置及跨任务 DAG 仍列为限制。文档有按月模式，而本次表单未见独立按月项。这支持定时触发的判断，不证明它具有我们的排期、并发资源或恢复保证。[Schedule](https://evose.ai/docs/en-US/use/schedule/)

官方 Library 文档主要讲组织内容分享，并把定时分享/自动归档列为未支持；当前页面已经呈现多类型产物，二者不能粗暴合并为“自动公司归档已实现”或“没有产物库”。[Library](https://evose.ai/docs/zh-CN/use/library/)

官方知识库说明区分查看、使用、编辑、管理，描述快照与可选审批；数据源另负责来源文件和解析。当前空库没有验证这些行为。[Knowledge Base](https://evose.ai/docs/en-US/use/build/data/knowledge-base/)、[Data Sources](https://evose.ai/docs/en-US/use/build/data/data-sources/)

官方技能说明包含草稿、发布、下线及组织分发；这支持方法沉淀的产品参考，不能代替运行固定版本与实际加载证据。[Skills](https://evose.ai/docs/zh-CN/use/build/capabilities/skills/)、[组织技能](https://evose.ai/docs/zh-CN/use/govern/tool/org-skill/)

官方角色/资源策略说明叠加角色与资源授权、拒绝优先；但当前同名资源策略页面实际上配置外部资源鉴权注入。必须分别记录，不能用文档覆盖真实页面。[Roles](https://evose.ai/docs/en-US/use/govern/organization/role/)、[Resource Policy](https://evose.ai/docs/en-US/use/govern/security/resource-policy/)

官方人员文档描述离职冻结访问与资产移交；当前仅见离职入口。Workspace 文档对 admin/owner 的删除能力存在口径差异；后续若验证需用不同角色账号，不自行选择有利解释。[人员部门](https://evose.ai/docs/en-US/use/govern/organization/staff-department/)、[Workspace Model](https://evose.ai/docs/en-US/use/build/concepts/workspace-model/)

官方凭据/桌面治理说明是后续负例来源，不能证明员工本地 harness 已受限或离线副本可立即清除。[凭据](https://evose.ai/docs/en-US/use/govern/security/credential-def/)、[桌面策略](https://evose.ai/docs/en-US/use/govern/desktop/policy/)

页面和文档未提供本轮能确认一致的部署版本。以上差异是待澄清事实，不据此宣称产品欺骗或后台缺陷。

## 4. 我们应借鉴的完整关系

以下是供下一轮交互评审的提案，不改变现行 PRD/PLAN 的阶段出口。

### 4.1 一个项目工作面

从我的工作进入项目，保持项目目标、获权成员、任务和资料上下文；中间切换总览、列表/看板/业务流程及后续排期，侧面可打开关联对话或任务线程，交付物能直接预览。收件箱处理待补充/待批准/待验收，活动与运行记录解释发生了什么。

这不是固定必须三栏：窄屏可收起侧栏。关键是同一工作不因切页丢失来源和权限。群、项目、小队仍不是一一对应；临时工作群不强制先创建项目，跨项目消息也不自动扩大受众。

### 4.2 三类状态不要混成一个字段

- 工作状态：待办、执行、待评审、完成等，沿 Multica 原生映射与明确扩展。
- 业务环节：例如需求、调研、制作、审核、交付；任务处于某环节，并可有并行子任务和依赖。
- 时间安排：计划起止、截止、依赖与实际时间分别维护；甘特只是投影，不能从 run 时间猜计划。

业务流程板不要求先造工作流执行引擎。后续定时触发也只生成同一授权命令/任务，由 Multica 唯一派发；不能让计划页自带第二调度器。

### 4.3 把项目知识和能力作为协作依据

项目明确列出：目标/验收要求、规则版本、参与真人/Bot、可用工具/skill、资料引用、共享记忆边界和维护责任。Bot 准入时记录实际采用的版本和来源；任务中变更规则形成新候选，不静默修改已执行输入。

### 4.4 用一次跨部门工作验证关系

1. 负责人提出内部活动方案目标，邀请市场/运营员工与资料/内容 Bot；普通员工也能发起同类小组。

6. 复盘产生规则/skill/小队模板改进候选，经验证与有权发布后供下次任务引用；不是把一次成功自动升级为生产技能。

### 7.5 用同一次业务走查，而非按竞品菜单分工

跨部门活动方案：负责人从我的工作进入原生 Project，真人担任项目 lead；需要协调时将父 Issue 交给原生 Squad，两个独立工作 Issue 分别由两员工 @ 资料 Bot/内容 Bot。项目描述放长期约定，任务附本次获权输入；Squad 指令只给队长，不能冒充全员授权政策。

资料结果先自动归档到任务，内容 Bot 消费固定获权版本；需要人决策时沿原生 Inbox/评论呈现同一事项。取消、待验收和成功交付分别显示，不能把原生项目进度或 stage closed 当全部成果成功。负责人验收指定交付版后，把方法纳入原生 skill 编辑/导入路径；候选/批准/实际加载差异按 C03/C04 补齐。后续有周报等真实周期需求，再启用原生 Autopilot create_issue；知识/表格和企微通道按已定后期范围接入。

**范围不变：**首轮原生任务协作；本期补安全、明确派工、固定输入、自动归档、当前权限与验收/计量，完整 P0 继续验证撤权和双机接续。后续企业治理界面以 Evose 为产品参考、Paperclip 为机制参考；可插面板/连接器优先原生 Plugin，核心强制点确需改源码则保留小而可追踪的上游补丁。不新开竞品后台，不重选技术栈，不把这张矩阵当已冻结接口或新开发授权。
