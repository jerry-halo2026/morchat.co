# 任务进度、工作空间与跨设备接续设计

> 2026-11-05，设计评审稿，尚未运行验证。Ethan 已要求先设计再证伪、保持中央协作控制＋员工本地完整 harness＋云端模型。Ethan 已确认“接续工作而不是搬进程”，且保存点必须自动、不依赖员工手动提交。本稿的具体技术组合与 R1/R2 实现仍须验证，也不是开工授权。

本文的任务保存点不自动构成 Bot 公共指令历史。当前指令正文仍由 Paperclip 管理，缺失的内容历史需显式复用原生 durable 加历史保留根，或公司既有保留资产自动归档，并与配置 revision、skill 版本形成能力清单；任务/run 引用实际使用清单。Bot 能力升级/回退不改变身份，也不替代本文件的工作接续协议。详见 [产品对象与版本](D:/dev/morchat.co/docs/PRODUCT-LIFECYCLE.md)。

## 1. 结论、方案与否决边界

推荐：Paperclip 保持任务/run 权威；公司 Git 管代码与适合版本管理的文本；受控对象存储管理二进制、工作中间态和恢复清单；每个执行尝试有独立本地工作区。优先适配 Paperclip 已有快照/恢复/写入代次机制，而非重新造一套调度或文件系统。具体证据见 [跨设备参考研究](D:/dev/morchat.co/docs/CROSS-DEVICE-REFERENCE-RESEARCH.md)。

| 方案 | 取舍 | 判定 |
|---|---|---|
| 所有人共享某台电脑、目录或常驻 Agent 进程 | 短期省同步；关机即失去工作，权限与并发污染 | 排除 |
| 所有产物都用 Git 分支/PR | 代码协作清晰；未提交文件、办公文件、执行效果和隐私并未自动解决 | 仅作为代码适配器，不作为整体平台 |
| 统一任务＋独立执行＋版本资产＋可验证保存点 | 支持人员/AI 分工、换机接手；必须补企业协议与故障测试 | 本轮推荐，待 Ethan 评审和 P0 实证 |

成立的目标是：不同工作可并行；有权限的继任者不依赖原员工电脑，能从公司已确认保存的进度与文件继续；旧机器回归不能覆盖新结果。不是每个 Agent 只能一个人用，也不是全公司排一条队。

不能同时承诺的事情：原机永远离线且唯一副本未上传仍零损失；所有授权设备都关机仍继续本地执行；未经控制的外部动作一定只执行一次；浏览器登录态、任意编辑器内存、任意 CLI 会话可无损搬家。若业务要求这些无条件成立，当前路线不成立，不能靠文案规避。

## 2. 分工单位：人、Agent、任务与运行分开

- 人类负责人承担业务结果；认领是责任变更，按当前任务版本原子成功一次，不等于占有整台设备或独占公司 Agent。
- 公司 Agent 在产品中就是 Bot（AI 同事），是可复用的稳定身份，不是模板、电脑或某次 run。同一个公用 Agent 可同时承接多个任务，每个任务的会话、工作区、工具权限和费用关联独立。
- 有多人/多 AI 共同推进一个目标时，拆成有输入版本、输出要求、依赖和验收人的子任务；不让所有人对一个可变目录同时写。
- 每个可写工作区由一个当前执行尝试拥有。需要并行探索同一任务就显式开子任务/候选分支，各自工作区，最后择优或合并；不能偷偷启动两个拥有同样正式写入权的 run。
- 员工助手仍默认本人授权设备；部门公用 Agent 按授权池选机。任务可转给继任者自己的助手或公用 Agent，但须有任务转派和资产访问权；这不等于继任者获得原员工电脑或私人助手会话。
- 同机、跨设备的无冲突任务均可并行。只有同一资源的写入、集成提交、独占 GUI/浏览器 profile 等需要局部协调；等待子任务的父任务释放可释放资源，不拿全局锁空等。

## 3. 权威数据与首版存储分工

| 对象 | 权威与持久位置 | 不应做的事 |
|---|---|---|
| 目标、任务、业务进度、依赖、责任与 run | Paperclip；企业扩展走受支持命令/明确补丁 | 群消息、客户端数据库另改一份任务状态 |
| 人、部门、设备池、资料授权 | morchat 企业与访问模块；关联 Paperclip 身份 | 用设备所有人替代任务责任人或数据授权 |
| 项目代码与文本正式版本 | 公司控制的 Git 仓库；记录仓库 ID 和精确 commit | 把员工个人 fork/本地 commit 当公司已持有 |
| 表格、报告、图片等及非 Git 目录 | 公司版本化资产存储；不可变内容与版本 ID | 文件同名就最后上传覆盖，强迫员工学 Git |
| 工作中间态与恢复清单 | 优先 Paperclip workspace/snapshot 扩展＋受控对象存储；任务指向获确认版本 | 只存最后交付、只存聊天、把 Agent 公共目录当项目盘 |
| 共享状态写入/外部动作回执 | 对应权威服务；任务关联操作 ID、已提交结果与未知项 | 本地日志说成功就算权威，重试另造操作 ID |
| 当前本地工作区 | task/run/attempt 独立目录，设备只是可替换执行副本 | 整盘同步、共享个人 HOME、把 worktree 当安全沙箱 |

公司拥有的是已纳管的工作内容和版本，不是所有员工磁盘内容。个人隐私、Cookie、Key、SSH 私钥、个人会话、无关历史不进入保存点。私密工作内容也可能是公司资产，但只对独立授权人可见。导入已有目录先确认工作范围、来源和排除项；敏感或凭据扫描是补充，不能保证发现全部隐私。

Git 分支/worktree 不是读权限隔离：同仓不同分支可能相互读取历史和对象。按可读范围分仓或分资产集，不把所有部门敏感内容放进公司单仓后靠分支名隔离。快照若包含仓库历史，必须校验整个被包含历史的授权，不只校验工作区可见文件。worktree 是本机多工作目录机制，跨机仍要获取提交和保存的字节。[Git worktree](https://git-scm.com/docs/git-worktree) · [Git 安全边界](https://git-scm.com/docs/git-push#_security)

## 4. 保存什么：保存点不是“AI 说做到 60%”

每个不可变保存点绑定以下清单；所有引用必须能在公司受控存储取得并校验，而非指向原机绝对路径：

| 清单部分 | 必需信息 |
|---|---|
| 归属与版本 | company/project/task、任务版本、run/attempt、写入代次、保存点 ID/父版本、创建与确认时间 |
| 已完成与未完成 | 已验收步骤、工作摘要、下一步、依赖及阻塞；AI 自报和已验证事实分别标注 |
| Git 恢复状态 | 仓库 ID、精确基线/HEAD、需保留的本地未推提交、index/暂存层、未暂存层、删除及已授权未跟踪文件；各自哈希/内容引用 |
| 非 Git 与输出 | 输入/中间态/候选成果的版本与哈希、目录结构/模式、允许的必要属性、明确排除和缺失项 |
| 已发生效果 | 中央已对账操作边界、结果引用、保存点之后已提交效果的查询线索、在途和未知项；不包含凭据值 |
| 继续执行条件 | harness/工具/skill 版本、依赖锁定信息、系统/能力约束、可重建环境配置、凭据与连接的引用 |
| 授权与来源 | 来源资源和权限版本、允许接手范围、数据级别；旧权限快照仅作追溯，恢复须查当前权限 |
| 完整性与提交证据 | manifest 摘要、对象校验与持久化回执、发布操作 ID、当前任务关联的确认回执 |

首版两类工作区均纳入：①受管理 Git 项目；②受管理普通文件夹。代码可隐藏 Git 操作于客户端；办公员工只看文件版本、差异和接手按钮。

Git 保存点要保住约定范围的未推 commit、staged/unstaged 区分、dirty 和获准 untracked 字节，不能简单自动 git add 全目录。恢复快照不是一次正式 commit，不污染业务主分支，也不自动成为被认可的交付。Git 本身的 push 不收集未提交工作。[Git push](https://git-scm.com/docs/git-push)

首版不保证任意旧仓库全部内部状态：正在 rebase/merge/cherry-pick、未知嵌套仓库、未登记 submodule/LFS、不可移植链接或文件名、只在应用内存的未保存内容，应拒绝标记“可跨机恢复”，列出原因，要求完成操作/显式导出/后续适配。普通二进制文件须支持版本保存；超出待定大小/容量边界时阻塞并明确告知，不静默漏掉。依赖缓存可重建，但所需依赖版本不可只存在原机。

## 5. 一致保存与发布协议

### 5.1 一致采集，不把一堆逐文件上传当同一时刻

1. runtime 在本任务工具安全边界短暂停止新的文件写入与效果发起，收敛已启动写入；冻结此工作区与任务事件截面，不阻塞其他任务。
2. 读取完整清单并复制为不可变暂存快照，验证路径、文件前后状态、Git 层次和内容哈希。必要时使用已验证的系统快照能力；实现选型留给 P0，但不能仅“扫描两遍没变化”便宣称任意并发写入下原子一致。
3. 人工修改也须通过客户端“接管编辑/导入版本”流程协调，不和 AI 在同一活动工作区抢写。普通编辑器未保存内存不在保证内；无法约束的外部写入使该保存点不具可恢复资格，不假定进程锁能锁住所有编辑器。
4. 快照冻结后可恢复该任务运算；上传的是冻结副本，不随正在工作的源目录变化。后续新工作仍标为未同步。超过容量、保存滞后阈值或上传失败时停止继续累积新产物，提示并保留唯一未确认副本。

### 5.2 对象先持久化，指针后生效

保存流程：准备 → 上传不可变内容 → 校验并固定保留引用 → 发布清单/任务关联 → 收到确认。临时对象、上传完成、可恢复保存点、正式交付是不同状态。

- 暂存上传使用公司/task/attempt 作用域与幂等 ID；每个对象验哈希、大小、路径和资源权限。Git 提交/恢复包、二进制对象、清单所引用内容全部可读且受保留策略保护，才允许发布。
- 保存点的当前写入代次、期望父保存点、任务版本和当前授权，必须在权威提交生效处重新核验。优先扩展 Paperclip 原生 workspace publication：同一事务确认当前代次、保存点指针与任务/run 关联，并产生可重放回执；应用不能直接改 Paperclip 数据库。
- 资产库和 Paperclip 不假装拥有跨库事务。资产先不可变暂存并建立受保护引用；Paperclip 确认关联才显示“公司已保存，可接手”。若公开 API 不能保证条件提交，P0 需受支持扩展/最小上游补丁；不能用 morchat 预检后普通 API 写入冒充原子性，也不另建第二个任务权威。
- 资产提交成功而关联失败：显示“已上传，关联待确认”，重试同一操作；不能误报完成，也不删除内容。关联成功但回执丢失：查询权威回执，不能重建任务或发布新版本冒充重试。
- 清理程序识别准备中、已确认、引用中、隔离证据和到期可删状态；不能按暂存时间误删提交中的对象。备份/恢复要覆盖任务关联、清单、Git 可达对象、二进制、加密解密材料和保留策略。远端 Git 仓库不是自动备份；删分支/GC 后恢复点仍须有受控引用或完整对象包。

### 5.3 自动保存是硬要求，不依赖员工或模型自觉

由 runtime/工作空间服务自动触发、采集、上传、确认与有界重试；不得依赖员工点击保存/同步、手动 Git commit/push、正常退出或给模型一句“记得保存”。主动保存只作辅助，不是接续前提。

输入准备完先确认初始点；受控工作单元/文件变更完成、等待人/子任务、受控暂停/交接前触发，有未确认变更时周期检查兜底。仅任务步骤/摘要/效果回执变化也纳入；持续编辑不能无限推迟，文件事件丢失仍须被周期比对发现。上传服务重启或 ACK 丢失后自动查询/补确认，不能要求员工手动补交。权限/代次失效则停止旧发布、转安全核对，不盲重试。

自动保存仍须一致截面与权威提交确认，不要求自动接受半成品、合并冲突或发布 skill。长工具须有可测阶段边界或受控分块/暂停；已落盘的纳管工作不能以“还没结束”为由长期不保存。任意编辑器未落盘内存不在首版保证内，不能用它掩盖支持目录已落盘内容的漏存。

保存周期、完成时限、未确认变更年龄/字节上限和故障至实际续作时限，执行实验前冻结，不能事后改通过标准。空闲不变的旧保存点不等于发生损失；超限/失败明确告警并阻止新增积压，不删除唯一未确认副本。阶段屏障、断电/断网/重连/冲突测法和失败条件见 [自动保存与最小双设备证伪方案](D:/dev/morchat.co/docs/DUAL-DEVICE-VALIDATION.md)；当前未执行，不承诺零损失。

## 6. 换机接手：恢复工作，不搬运活进程

### 6.1 自动接续的两条安全路径（本轮建议修订）

前稿把“可信证明旧进程停止”作为所有接续的共同前提，过于保守：网络分区时可能永远拿不到原机停止证据。建议改成以下两类，**不是租约过期一律重跑**：

| 执行类别 | 允许新尝试的条件 |
|---|---|
| R1：可重复计算＋仅独立尝试目录写入，所有共享发布/任务修改/模型准入均受中央控制 | 旧代次在所有权威提交点已被隔离，相关在途提交已收敛或可核对；输入/保存点完整可读且重做安全。即使无法证明旧进程物理停止，也可在新隔离目录继续；旧机最多留下不能发布的局部计算结果 |
| R2：涉及独占本机资源、不可重放或未被中央隔离的动作 | 须确认旧执行/资源安全终止，并对账所有已提交和未知效果；未知则阻塞有权人核对，不自动转派 |

R1 是经过验证的能力契约，不由模型或任务标签自行宣告。必须证明受控 shell/Python/Node 无途径写其他任务目录/公司 Git 正式分支/共享资产，且没有可绕过中央的业务凭据、网络写能力和浏览器登录态；未获验证的完整 CLI、任意 GUI 或外部编辑器一律不归 R1。工作区隔离和 worktree 本身不足以证明这些。中央失联时仍停止新模型/工具动作；已启动局部计算可能收敛较慢，不意味着拥有发布权。

两类都要对账保存点之后的已提交子任务、文件/资产和操作回执；在途请求不能因为换代就假定没发生。真实第三方业务首版只读；测试重复发送/写入只能用合成业务与隔离账号。无法集中拦截的第三方动作不承诺 exactly-once。

### 6.2 接手步骤

1. 确认接手的是新任务还是旧任务接续；新任务使用最新获授权输入，不能误拿别人的活动工作区。
2. 对旧任务选择最近完整且权限仍满足的保存点；列明其后未确认内容。旧尝试失去当前写入权，按 R1/R2 分类形成中央恢复边界和跳过/续做/待核对清单。
3. 按员工助手绑定或公用 Agent 设备池重新选机，验证接手人、Agent、设备宿主的数据承载权与工具条件。没资格/全部离线则明确等待，不借用任意同事电脑、不中央代跑。
4. 在新尝试的空工作区拉取精确版本，校验完整哈希/Git 状态与依赖；不覆盖 B 已有目录。不可移植输入/路径列为阻塞，不用“相同路径”冒充相同内容。
5. 用当前授权的工作摘要、任务事实、文件和剩余步骤新建 harness 会话；原始 session 不是必需条件。仅同版本且权限安全经专门验证的会话可选择恢复；不复制 Cookie/个人 Key。
6. 新设备发准备确认后，权威条件提交激活新 run/attempt；重复启动消息不重复创建有效运行。恢复下载/校验失败不得推进任务状态到正常执行。
7. 新尝试完成后生成新保存点和候选交付。旧机重连先核对代次；它的独有改动只能提交隔离证据/候选补丁，不能覆盖新保存点或交付。身份已撤销时拒绝旧凭证，由有权接管人恢复导入。

保存点内的权限不能复活旧权限；整包含新接手人无权内容时禁止下载，不做先给全包再靠提示词过滤。必要时由有权限的人发布安全交接版本，保留原任务受限资料。

## 7. 并行汇合与进度呈现

代码：子任务在各自分支/worktree 生成候选 commit，提交到公司受控远端。集成按预期基线、测试与审查决定是否合并；目标分支变化须重新校验。正式分支不开放给本地 AI 任意直接推送；仅中央受控发布路径可生效。运行可并行，目标分支提交点需要有序不等于全员排队。

办公资产：报告、表格、图片等按版本登记。多人修改同一版本时保留候选分支，选择/人工合并/独立生成合并版本；不能对二进制假装执行 Git 自动三方合并。人工修订也是新版本，不静默覆盖已确认点。

看板/任务卡至少展示四个独立维度：

- 业务：待认领、进行、阻塞、待验收、已验收，由 Paperclip 事实映射，不由聊天自报。
- 执行：在谁的授权设备运行、等待依赖、设备失联、恢复中、结果未知。
- 保存：仅本机、上传中、公司已确认到哪个步骤/时间、存在未确认改动、保存失败。
- 交付：候选文件/分支、待检查/合并、已接纳版本；“保存成功”不自动改为任务完成。

同部门/跨部门按现有授权展示相应业务流转；无权者不见文件名、清单、进度摘要或隐含敏感信息。老板和负责人看同一事实的不同授权投影，不是另一份进度表。

## 8. 用实际公司工作走一遍

示例：负责人在跨部门项目群下达“形成下一期经营改进方案”。运营负责数据诊断，内容部门负责素材建议，财务只分享获准的汇总成本；千川只是一项只读数据来源，也可替换为销售台账。

1. 负责人建目标及子任务，员工认领；一个部门公用分析 Agent 可同时协助运营数据分析和另一项目，不共享可变会话。
2. A 的授权电脑执行数据读取和 Python 清洗，保存输入数据版本、分析脚本、未完成报告和表格。B 的电脑并行写素材建议，财务助手生成获准摘要。三项工作无需等待某个公共 Agent 进程“空闲”。
3. A 的 runtime 自动发布保存点 CP-1，无需员工手动提交：公司确认脚本精确版本、表格字节、已完成清洗步骤和剩余分析；CP-1 是可接手中间态，不是正式交付。随后产生但未确认的 CP-2 仍显示本机待同步。
4. A 突然断电。B 如只是有新分析任务，直接在合格设备建立新 run；不抢 A 的工作目录。若需要接手 A 的任务，经责任/授权处理后，从 CP-1 在合格设备重建。R1 经证实则可接续；若包含未知业务写动作/不可迁移输入，则明确阻塞。不能声称 CP-2 也已找回。
5. 新设备继续分析，不重复创建 CP-1 之后已在中央创建的子任务/成果。原机重新上线，独有材料进入待核对候选，不能反向覆盖新分析结果。
6. 各子任务交付版本由负责人检查、集成；群/面板展示交接和阻塞。最后把验证有效的方法提炼为 skill 候选，去掉个人路径/凭据，以案例验证后发布部门版本；保存点不自动升级为通用 skill。

## 9. 可证伪门禁：未测不算通过

以下是 P0 实验设计，不是本轮已执行的测试。先按 [自动保存与最小双设备证伪方案](D:/dev/morchat.co/docs/DUAL-DEVICE-VALIDATION.md) 运行最小双设备子集，仍不替代完整 WC/DC 门禁。至少两台实际授权设备和一台不合格设备；运行所选真实 harness、Paperclip 接口和存储路径，使用合成业务数据。不能只关闭聊天窗口代替执行节点断电，也不能只看 UI 状态判断恢复。

| ID | 故障或反例 | 必须观察到的结果；否则否决对应能力 |
|---|---|---|
| WC-01 | 同 Agent 多子任务，同机及异机执行；两调度器重复派同逻辑工作 | 独立任务真实重叠执行、会话/目录隔离；相同逻辑工作只有一个有效启动，非全局串行 |
| WC-02 | Git 有未推 commit、staged/unstaged、删除、获准 untracked；普通目录有二进制表格；确认保存后原机断电 | B 从空目录恢复约定 Git 分层及全部内容哈希、任务版本，且工具确实在 B 执行 |
| WC-03 | 两个关联文件/任务事件在采集中变化，或外部编辑器抢写 | 得到同一受控截面的版本，或明确拒绝；不可混合版本仍标可接手 |
| WC-04 | 上传部分失败；所有对象成功但任务关联失败；关联成功但 ACK 丢失；并发清理 | 最多发布一个一致保存点，可查询同一回执；不误报保存、不误删关联中对象、不重复业务操作 |
| WC-05 | 全程无手动提交，事件/周期自动保存；确认前硬断电、回传重启、磁盘满、长工具无安全点 | 自动保存和重试独立于员工/模型自觉；显示最近已确认点与真实缺口，超限暂停告警，支持工作负载不能永远不保存；测出损失/恢复界限 |
| WC-06 | A 网络分区但进程继续；R1 由 B 接手，A 请求在预检后冻结直到换代再提交 | 新尝试能安全推进；旧提交在生效处被拒；不能绕过网关推正式分支/写资产/消费模型。若做不到，R1 路径不成立 |
| WC-07 | 合成外部动作已成功但回执未记；保存点后已建子任务/资产；启动 ACK 丢失 | 中央对账跳过已提交，未知阻塞，不能重发；不以换 attempt ID 绕过防重 |
| WC-08 | 两子任务改同一文本/二进制，再让旧设备回传 | 候选隔离、冲突明确、基线校验；无静默覆盖、无错误宣布合并成功 |
| WC-09 | 第三台拿到 ID；成员调岗/离职/资料升敏；快照含受限分支历史或私人文件 | 未授权不获数据/执行/费用能力；不给旧 session/整包越权；来源限制不因交接放宽 |
| WC-10 | 新设备不同系统/版本/路径，依赖或 LFS/submodule 缺失，未完成 rebase | 兼容则校验后恢复，不兼容明确阻塞；不得略过缺失内容继续宣布成功 |
| WC-11 | 原公司控制节点/存储恢复旧备份，Git 分支删掉、对象 GC、旧账号已撤销 | 可恢复的保存点闭包与解密材料完整；不能复活旧授权/代次，已完成效果不重放；与 DC-08 联合验证 |
| WC-12 | 继任者操作全链路，员工助手离线与公共池全离线各一次 | 继任者只取获授权内容；助手不借别人电脑，公用池按规则选；全离线诚实等待；保存/执行/验收四种状态一致 |

任何数据越权、丢失已确认版本、旧写覆盖、新旧重复业务效果、用单任务限制冒充并行均是阻断项。实现缺陷可在已确认边界内修复并复测；若必须中央代跑、下发原始 Key、扩大设备权限或取消基本分工才能成立，否决当前组合。R1 若无法验证，不能悄悄以“永远等待原机”满足无人值守接手要求，须回到 Ethan 评审范围/执行隔离方案。

## 10. 复用、自建与建设顺序

- 优先复用/适配 Paperclip 的任务/workspace/snapshot、上传回执、代次校验和持久指针；其当前 remote workspace 路径绑定 runner＋sandbox，不直接代表员工节点适配已完成。Agent 公共目录的 last-sync-wins 不能用作多人项目正式文件合并。
- OpenMausBot 借文件传输校验、冲突保留、保存新鲜度与桌面交互；不照搬原机权威/个人云/离职删除策略，不把云上运行 Agent 作为我们默认方案。
- Horde 借按能力与项目授权选设备、子任务独立目录、结果基线验证；不替代 Paperclip 任务权威，不能将其明确不支持的异机续跑算现成能力。
- Code Coordinator 借 issue→分支→PR 与集成门禁；许可和安全边界不适合作为直接产品底座。OpenHands SDK 等作为归档/事件模块备选，不再叠加另一套完整平台。
- 自建/适配企业部分：本地节点协议与受控工作区、企业保存点清单与事务关联、R1/R2 能力证明及恢复对账、当前权限/留存/离职规则、非代码资产交付与员工端提示。已有底层模块不重复实现，缺口不能靠组件名替代测试。

DSH优先的Windows路径需注意：外部adapter接通不自动获得PCWS入口；固定样本限制在paperclip_runner＋sandbox，需要显式节点capture/restore/transport扩展，保留中央epoch/writerRunId/parentSnapshot事务。MXC进程退出、DSH会话日志落盘均不等于公司文件确认。具体证据与WI-08见 [Windows DSH接入](D:/dev/morchat.co/docs/WINDOWS-DSH-INTEGRATION.md)。

建设顺序：P0 先做 [原生运行与 Harness 核查](D:/dev/morchat.co/docs/NATIVE-RUNTIME-RESEARCH.md) 的原生/多协议预检与选路，经授权建设必要接入后完成两端 NG 门禁，再做两台 Windows 11 x64 原生双向 DV 与完整 WC/DC 证伪；固定一个引擎候选；P1 把普通目录＋Git 工作区的保存/接手、最薄看板四状态放进纵向切片；P2 补跨部门交付、冲突与离职闭环；P3 测试规模、备份和双业务场景。暂缓热迁移、任意应用实时共编、复杂 Git 内部状态恢复和工作流画布。首轮 Windows 优先、Mac 预备已由 Ethan 确认，不把 Mac 实现/跨系统验收设为首轮条件；具体 Windows build/文件规模、候选保存损失窗口与恢复时限、试点资料授权在 P0 执行前确认。参数见双设备规程，不是隐含上线保证。
